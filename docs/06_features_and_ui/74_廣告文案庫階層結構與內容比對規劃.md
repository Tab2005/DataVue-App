# 74_廣告文案庫：階層結構與內容比對規劃

> 延伸 [73_廣告文案庫功能實作規劃](73_廣告文案庫功能實作規劃.md)。73 只抓「廣告」一層；本文件補上行銷活動與廣告組合的設定參數，並把三層串成完整的階層脈絡，同時把廣告拆成「文案／素材」元件做比對，作為後續 AI 分析的資料基礎。

## 背景

73 上線後已能正常抓取自家廣告帳號的廣告文案。下一步的需求：

1. 把**行銷活動（campaign）**與**廣告組合（adset）**的設定參數抓下來，整理到各廣告帳號底下。
2. 依「廣告帳號 → 行銷活動 → 廣告組合 → 廣告」把上下層串起來，例如行銷活動 A 底下有廣告組合 A、B，各自底下又有數則廣告。
3. 同一廣告組合內常見「文案相同、素材不同」或「素材相同、文案不同」的測試組合，需要能自動辨識。
4. 整理後的資料要能交給 AI 模型做分析。

## 拍板決策（2026-10-14）

1. **沿用 `ad_library` 模組與現有授權**，不新增模組權限或 FB 權限；token、`ads_read` 範圍、分頁與 rate limit 處理沿用 73 的 `data_source.py`。
2. **廣告拆成內容元件比對**：每則廣告拆成主要文字、標題、說明、圖片、影片等元件，各自計算指紋，再以「文案鑰匙」與「素材鑰匙」判定廣告之間的關係。
3. **文案相同的判定採「正規化後完全相同」**。近似比對（改了 emoji、標點也算同一段）先不做，日後再以相似度門檻或 embedding 補上。
4. **比對範圍限同一廣告帳號內**，與現有帳號授權邊界一致。跨帳號比對涉及權限，有需求再另開。
5. **影片以 `video_id` 識別，接受已知限制**：同一支影片重複上傳會拿到不同 `video_id`，第一版會被判為不同素材；之後再考慮用縮圖或影片雜湊補強。
6. **AI 分析另開文件**：本文件只負責把資料抓齊、串好，並提供給 AI 用的精簡輸出端點；提示詞設計與 UI 留到下一份規劃。

## 一、階層資料：行銷活動與廣告組合

### 現況

- `ad_library_items` 已有 `campaign_id`、`campaign_name`、`adset_id`、`adset_name`、`objective`（`normalizer.py` 從 `campaign{...}`、`adset{...}` 欄位展開），**廣告到上層的關聯已經存在**，只缺上兩層本身的設定參數。
- 專案內 `service_modules/facebook_api.py` 的 `fetch_campaigns`／`fetch_adsets` 只抓名稱等少量欄位，不沿用；在 `ad_library/data_source.py` 新增專用函式。

### Graph API 抓取

| 端點 | 欄位 |
|---|---|
| `GET /{act_id}?fields=currency,timezone_name` | 帳號幣別（換算預算用）、時區 |
| `GET /{act_id}/campaigns` | `id,name,objective,status,effective_status,buying_type,bid_strategy,daily_budget,lifetime_budget,budget_remaining,special_ad_categories,smart_promotion_type,start_time,stop_time,created_time,updated_time,insights.date_preset(maximum){impressions,reach,spend,clicks,ctr}` |
| `GET /{act_id}/adsets` | `id,name,campaign_id,status,effective_status,optimization_goal,billing_event,bid_strategy,bid_amount,daily_budget,lifetime_budget,budget_remaining,targeting,promoted_object,attribution_spec,destination_type,is_dynamic_creative,start_time,end_time,created_time,updated_time,insights.date_preset(maximum){impressions,reach,spend,clicks,ctr}` |

- 分頁、`limit=100`、頁間 sleep、rate limit 錯誤碼 `{4, 17, 32, 613, 80004}` 的 partial 處理全部沿用 `fetch_ads` 的寫法。
- 預設也抓已封存的物件（`effective_status` 包含 `ARCHIVED`），與 73 的廣告抓取範圍一致；刪除的物件 API 不回傳，以 `last_seen_at` 標記「本次刷新沒看到」。
- **預算單位**：`daily_budget`／`lifetime_budget`／`bid_amount` 為帳號幣別的最小單位。DB 存原始整數 + `currency`，換算在輸出層依 Meta 公布的幣別 offset 處理（大多數幣別 ÷100，少數無小數幣別 ÷1），不在入庫時換算。
- **targeting 原樣存 JSON**，另抽幾個常用摘要欄位（年齡範圍、性別、國家／地區、是否 Advantage+ 受眾、版位）供篩選與 AI 精簡輸出。自訂受眾以 targeting 內回傳的 `{id, name}` 為準。

### 刷新流程調整

`service.run_refresh` 依序執行，仍是同一個 job：

1. 抓帳號幣別
2. 抓 campaigns → upsert `ad_library_campaigns`
3. 抓 adsets → upsert `ad_library_adsets`
4. 抓 ads（現有流程，含素材落地）
5. 由 ads 萃取內容元件 → upsert `ad_library_contents`、重建該帳號的 `ad_library_ad_contents`
6. （第 3 階段）對動態素材廣告抓元件成效

`ad_library_refresh_jobs` 新增 `campaigns_fetched`、`adsets_fetched` 計數，前端進度顯示一併更新。任一步撞 rate limit 時保留已抓到的資料、job 標為 `partial`，與 73 相同。

> 注意：廣告仍受 73 的單次上限 `max_ads=2000`。超過時樹狀結構會有廣告組合「看起來沒有廣告」，job 為 `partial`，前端需提示。

## 二、內容元件與比對

### 元件與指紋

| 元件 kind | 來源 | 指紋 |
|---|---|---|
| `primary_text` | `primary_texts[]` | 正規化後 sha256 |
| `headline` | `headlines[]` | 同上 |
| `description` | `descriptions[]` | 同上 |
| `image` | `media[].image_hash` | `img:` + `image_hash` |
| `video` | creative `video_id`（動態素材取 `asset_feed_spec.videos[].video_id`） | `vid:` + `video_id` |

**文字正規化**（`fingerprint.py`，純函式）：

1. Unicode NFKC（統一全形／半形英數與標點）
2. `\r\n`、`\r` → `\n`
3. 每行去除尾端空白，連續 3 行以上空行壓成 1 行空行
4. 去頭尾空白
5. 空字串不產生元件

emoji 與大小寫保留，不做進一步處理，以符合「完全相同」的決策。

**取不到 `image_hash` 的素材**（例如部分以既有貼文 `effective_object_story_id` 投放、只有 URL 的廣告）：不產生素材元件，該廣告 `media_key` 為空，不參與素材面的比對，避免以會過期、帶簽章參數的 CDN URL 誤判。

### 廣告的兩把鑰匙

每則廣告在 `ad_library_items` 存兩個欄位：

- `copy_key`：該廣告所有文字元件指紋，依 `kind` 分組、組內排序後串接，再取 sha256。
- `media_key`：所有素材元件指紋串接後取 sha256。**輪播保留卡片順序**（順序不同視為不同素材組合）；動態素材則排序後串接（順序由系統決定，沒有意義）。

### 關係判定

在同一範圍（預設同一廣告組合，也可選同一行銷活動）內兩兩比較：

| 文案 `copy_key` | 素材 `media_key` | 關係 | 分析用途 |
|---|---|---|---|
| 相同 | 不同 | `media_test` 素材測試 | 文案固定，比較素材 |
| 不同 | 相同 | `copy_test` 文案測試 | 素材固定，比較文案 |
| 相同 | 相同 | `duplicate` 重複投放 | 多為複製出來的廣告，可合併看 |
| 不同 | 不同 | `independent` 獨立 | 不做配對比較 |

輸出以「組」為單位，而不是兩兩配對，避免組合爆炸。例如：

```
廣告組合 A
├─ 廣告 1：文案 T1 + 圖片 M1
├─ 廣告 2：文案 T1 + 圖片 M2
└─ 廣告 3：文案 T2 + 圖片 M1

→ media_test 組（固定 T1）：廣告 1（M1）、廣告 2（M2）
→ copy_test  組（固定 M1）：廣告 1（T1）、廣告 3（T2）
```

關係**於查詢時計算**（對 `copy_key`、`media_key` 做 group by），不落地存表；資料量在單帳號數千則廣告內，即時計算即可。

### 成效歸屬的前提

- 一般廣告的成效只有廣告層級。「文案測試」比較的是兩則廣告的成效，只是素材這個變因被固定，**不代表能把成效拆給文案本身**。此前提需寫進提供給 AI 的資料說明與提示詞中，避免過度推論。
- 文案相同的廣告若分屬不同廣告組合（受眾不同），比較時要把廣告組合設定一併帶出，交由分析判斷差異來源。

### 動態素材（第 3 階段）

動態素材／Advantage+ 素材的廣告（`asset_feed_spec` 或 adset `is_dynamic_creative=true`）一則就含多段文案與多張圖，整體成效無法拆給元件。改抓 insights 的元件 breakdown：

- `GET /{ad_id}/insights?breakdowns=body_asset`、`title_asset`、`description_asset`、`image_asset`、`video_asset`
- 每種 breakdown 需各自呼叫（不能互相組合），只對動態素材廣告執行，以控制呼叫量。
- 回傳的元件以文字或 hash 對回 `ad_library_contents`，存入 `ad_library_asset_insights`。
- 實作時先以真實帳號實測回傳格式與可用的 breakdown，再定稿欄位對應。

## 四、API 端點（前綴 `/api/ad-library`，沿用 `require_ad_library_module`）

| 端點 | 說明 | 授權 |
|---|---|---|
| `GET /tree?account_id=&status=` | 帳號 → 行銷活動 → 廣告組合 → 廣告的巢狀 JSON；廣告節點只帶摘要（名稱、狀態、鑰匙、成效、首段文案），詳情走既有 `/ads/{item_id}` | 帳號 403 |
| `GET /campaigns/{id}` | 單一行銷活動完整設定 | id 查詢 404 |
| `GET /adsets/{id}` | 單一廣告組合完整設定（含 targeting） | id 查詢 404 |
| `GET /comparisons?account_id=&scope=adset\|campaign&relation=` | 依第二節規則輸出 `media_test`／`copy_test`／`duplicate` 組 | 帳號 403 |
| `GET /contents?account_id=&kind=&q=&sort=` | 元件清單，附使用次數、用在哪些廣告組合、彙總成效 | 帳號 403 |
| `GET /contents/{id}` | 單一元件與使用它的所有廣告 | id 查詢 404 |
| `GET /ai-context?account_id=&campaign_id=` | 給 AI 用的精簡 JSON（見下） | 帳號 403；campaign 不屬於該帳號 → 404 |

授權規則沿用 73：帶 `account_id` 的端點走 `verify_account_access_or_403`，以 id 查資源的端點走 `verify_resource_access_or_404`。

### `/ai-context` 輸出原則

- 以**行銷活動為單位**輸出，避免單次資料過大（不帶 `campaign_id` 時只回行銷活動清單與摘要）。
- 文案以元件 id 參照，元件內容只列一次（`contents` 字典），避免同一段文案在多則廣告重複出現。
- 帶上廣告組合的 `targeting_summary`（不帶原始 targeting）、預算換算後的金額與幣別、比對組結果。
- 附 `notes` 欄位說明成效歸屬前提（第二節）。

- 前端：結構樹與比對檢視的基本渲染、空狀態、`partial` 提示。

## 部署注意事項

- 不需新增環境變數或 FB 權限。
- migration 隨部署由 `run_migration.py` 自動執行（Dockerfile CMD），失敗時 web 不會啟動，部署後確認服務為 RUNNING。
- 舊資料在第一次刷新後才會有行銷活動、廣告組合與元件資料，上線後需請使用者對各帳號重新抓取一次。

## 風險與待確認

- **API 呼叫量**：每次刷新多 2～3 次分頁呼叫，影響小；第 3 階段的 breakdown 呼叫量與動態素材廣告數成正比，需設上限並只抓有曝光的廣告。
- **2000 則廣告上限**：超過時樹狀結構不完整（見第一節注意事項），之後可改為增量刷新。
- **影片重複上傳**：同一支影片不同 `video_id` 會被判為不同素材（已接受的限制）。
- **targeting 欄位隨 API 版本變動**：摘要欄位抽取需容錯，取不到就留空，原始 JSON 仍保留。
- **幣別 offset**：需對照 Meta 公布的幣別清單實作，並以帳號實際幣別測試。
- **Volume 用量**：本文件不新增素材落地，用量與 73 相同。
