# 73_廣告文案庫（Ad Library）功能實作規劃

## 背景

使用者希望有一個類似 Meta 官方「廣告檔案庫」（facebook.com/ads/library）的功能分頁，集中瀏覽、搜尋、排序**團隊自家廣告帳號**投放過的廣告文案與素材，方便回顧文案、挑選高成效文案再利用。

### 資料來源取捨（已拍板：做法 A）

| 做法 | 資料來源 | 結論 |
|---|---|---|
| **A. 自家廣告帳號** | Marketing API `/{act_id}/ads`（沿用既有 `TokenManager` token） | ✅ 採用。合規、可取得完整文案與成效數字 |
| B. 競品粉專 | Ad Library API `/ads_archive` | ❌ 不做。台灣地區只回傳政治／社會議題廣告，一般商業廣告僅限「投放到歐盟」者，且不支援依曝光排序 |
| C. 爬取 facebook.com/ads/library | 網頁爬蟲 | ❌ 不做。違反 Meta 使用條款，會連帶危及本系統的 App 與 Token |

## 拍板決策

1. **獨立模組權限 `ad_library`**：新增模組 key `ad_library`（不沿用 `fb_ads`），採 module-only access、不分細項權限（同 `contribution`、`meta_andromeda`）。上線後需由管理員在權限管理頁授予團隊／使用者。
2. **前端新建獨立分頁** `/ad-library`（`AdLibrary.jsx`），側欄新增選單項目。
3. **帳號層級授權**：所有帶 `account_id` 的端點一律走 `resolve_accessible_account_ids`，與 `fb_ads/router.py::_ensure_account_access` 同一套邏輯（呼應 commit `44b1c5c` 的白名單修補）。
4. **素材持久化沿用正式環境既有的 Meta Andromeda 儲存管線**（詳見下節），不另開新的 Volume 或 S3 bucket。
5. **本地快取表 + 手動／背景刷新**：讀取走 DB（快、可搜尋排序），抓取 FB 由 `POST /refresh` 觸發背景任務，模式同 `contribution` 的 `/data/refresh`。

## 正式環境儲存現況（2026-10-14 查核）

Zeabur 專案 `DataVue-App`（`695f487b...`）服務：`frontend`、`backend`、`postgresql`、`redis`、`meta-andromeda-worker`。

| 服務 | `SERVICE_ROLE` | `META_ANDROMEDA_STORAGE_BACKEND` | `META_ANDROMEDA_STORAGE_ROOT` |
|---|---|---|---|
| `backend` | `web` | `filesystem` | `/app/backend/storage/meta_andromeda` |
| `meta-andromeda-worker` | `worker` | `filesystem` | `/app/backend/storage/meta_andromeda` |

- `backend` 另設 `META_ANDROMEDA_INTERNAL_WORKER_BASE_URL=http://meta-andromeda-worker.zeabur.internal:8080`。
- 即 [docs/28](../03_meta_andromeda/28_Meta_Andromeda_素材縮圖跨容器儲存問題與Worker集中化方案規劃.md) 的 Option D：**素材檔案唯一由 worker 的持久化 Volume 持有**，web 透過內網 HMAC 驗證的 `/internal/meta-andromeda/assets` 轉發上傳與讀取。
- 未使用 S3／R2；Zeabur 專案內也沒有獨立的物件儲存服務。
- 尚未確認：worker Volume 的容量與目前用量（`service exec` 查詢被自動模式擋下，需使用者自行在 Zeabur 控制台確認）。

### 對本功能的影響

- web 容器**沒有**素材 Volume，不能直接寫檔 → 必須沿用既有的轉發機制。
- 既有程式可直接重用：
  - 上傳：`internal_asset_gateway.proxy_asset_upload_response(asset_type, source_filename, file_bytes, uploaded_by, content_type)`（`SERVICE_ROLE=web`），或 `MetaAndromedaService.upload_asset(...)`（`SERVICE_ROLE=all`，本地開發）。分流判斷比照 `meta_andromeda/router/scoring_assets.py:71`。
  - 讀取：`internal_asset_gateway.proxy_asset_preview_response(uri)`／`asset_delivery.build_asset_response(asset)`。
  - 紀錄表：`meta_andromeda_assets`（`asset_type="image"`，可通過既有驗證並自動壓縮 >400KB 圖片）。
- 現有 `/api/meta-andromeda/assets/...` 預覽端點受 `meta_andromeda` 模組權限保護，ad_library 使用者不一定有該權限 → **本模組需自己的預覽端點**，做完帳號授權檢查後再呼叫 `proxy_asset_preview_response`。

### 儲存範圍（控制 Volume 用量）

- **只落地圖片**：單圖廣告的 `image_url`、影片廣告的縮圖、輪播的每張卡片圖。
- **影片不落地**：前端顯示縮圖，點擊開啟 FB 的 `preview_shareable_link`。
- **依 FB `image_hash` 去重**：同一張圖片被多支廣告使用時只存一次（以 `account_id + image_hash` 對應到同一個 `asset_id`）。
- 下載失敗不阻斷刷新：該筆 `media_asset_id` 留空，前端退回顯示 FB CDN 原網址（可能已過期，顯示佔位圖）。

## 技術方向

### 後端：新模組 `backend/modules/ad_library/`

結構比照 `modules/contribution/`：

```
modules/ad_library/
├── __init__.py
├── data_source.py     # 打 Graph API：分頁抓 ads + creative + insights
├── normalizer.py      # creative → 文案欄位攤平（含動態創意 asset_feed_spec）
├── media.py           # 下載圖片、依 SERVICE_ROLE 分流存入 worker storage
├── repository.py      # ad_library_items / ad_library_refresh_jobs CRUD
├── service.py         # refresh 流程編排
├── dependencies.py    # 帳號授權（包 resolve_accessible_account_ids）
├── schemas.py
└── router.py
```

#### Graph API 抓取

```
GET /{act_id}/ads
  ?fields=id,name,effective_status,created_time,updated_time,
          adset{id,name},campaign{id,name,objective},
          creative{id,body,title,object_story_spec,asset_feed_spec,
                   call_to_action_type,image_url,image_hash,thumbnail_url,
                   video_id,effective_object_story_id},
          preview_shareable_link,
          insights.date_preset(maximum){impressions,reach,spend,clicks,ctr}
  &limit=100
```

- 依 `paging.next` 逐頁抓，單次刷新設上限（預設 2,000 支廣告），避免撞 rate limit。
- 遇 Graph error code 17／80004（rate limit）時停止並將 job 標為 `partial`。
- 文案攤平規則（`normalizer.py`）：
  - 一般創意：`object_story_spec.link_data.{message,name,description,call_to_action}`、`video_data.{message,title,call_to_action}`，fallback 到 `creative.body/title`。
  - 輪播：`link_data.child_attachments[]` 每張卡片的 `name/description/picture/image_hash`。
  - 動態創意：`asset_feed_spec.{bodies,titles,descriptions,call_to_action_types,images,videos}` 全部保留成陣列。
- `media_type`：`image`／`video`／`carousel`／`dynamic`。

#### API 端點（前綴 `/api/ad-library`，全部 `Depends(require_module("ad_library"))`）

| 方法 | 路徑 | 說明 | async/sync |
|---|---|---|---|
| GET | `/ping` | 模組存活檢查 | `def` |
| GET | `/accounts` | 本模組可用的廣告帳號（已套用團隊白名單）；不依賴 fb_ads 的 `/api/ad-accounts`，讓只有 ad_library 權限的使用者也能選帳號 | `async def` |
| POST | `/refresh` | body `{account_id}`；帳號授權後建立 job，回 202 + job_id；同帳號已有執行中 job 則回 409 | `async def` |
| GET | `/refresh/{job_id}` | 查 job 狀態（驗證 job 的 account 可視，否則 404） | `def` |
| GET | `/ads` | `account_id`（必填）、`status`、`media_type`、`q`、`sort`（impressions／spend／ctr／created）、`order`、`page`、`page_size` | `def` |
| GET | `/ads/{item_id}` | 單筆詳情 | `def` |
| GET | `/media/{asset_id}` | 驗證該 asset 屬於可視帳號的某筆廣告後，轉發 worker 取圖 | `async def` |
| GET | `/ads/export` | 同 `/ads` 篩選條件匯出 CSV（UTF-8 BOM，Excel 可直接開） | `def` |

- 依 2026-07-08 凍結事故慣例：讀寫同步 DB 的端點宣告為 `def`；`async def` 端點內的同步 DB／Redis 呼叫一律包 `asyncio.to_thread`。
- 帳號授權失敗回 403；以 id 查詢（job、item、media）不可視時回 404，避免洩漏存在性。
- 背景任務：`BackgroundTasks` 呼叫 `service.run_refresh(job_id)`，內部 `asyncio.to_thread` 包 DB 操作，媒體下載以 `asyncio.Semaphore(4)` 限制並發。

## 部署注意事項

- 不需新增環境變數，沿用 `META_ANDROMEDA_STORAGE_*` 與 `META_ANDROMEDA_INTERNAL_WORKER_*`。
- 部署後需執行 alembic migration（依既有部署流程）。
- 需由管理員授予 `ad_library` 模組權限，使用者才看得到側欄選單。
- 建議上線前在 Zeabur 控制台確認 `meta-andromeda-worker` Volume 剩餘容量。

## 風險與待確認

- **Rate limit**：大帳號（上萬支廣告）單次刷新可能撞限制 → 已設單次上限與 partial 狀態，後續可改為增量刷新（只抓 `updated_time` 之後的廣告）。
- **Volume 共用**：與 Meta Andromeda 素材共用同一顆 Volume，用量增加需留意；若日後改 S3，只要切換 `META_ANDROMEDA_STORAGE_BACKEND`，本模組不需改程式。
- **素材存在 `meta_andromeda_assets` 表**：2026-10-14 檢查時專案內沒有清理孤兒素材的腳本；日後若新增，需排除被 `ad_library_items.media` 參照的 asset。
- **服務重啟中斷刷新**：背景任務隨程序消失，job 會停在 running；超過 30 分鐘的 queued／running job 不再擋下新的刷新（`repository.STALE_JOB_AFTER`）。
