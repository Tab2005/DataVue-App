# 75_廣告文案庫：AI 分析規劃

> 延伸 [74_廣告文案庫階層結構與內容比對規劃](74_廣告文案庫階層結構與內容比對規劃.md) 第 4 階段第 13 步。74 已完成資料基礎（階層、內容元件、比對組、動態素材元件成效）與給 AI 用的 `GET /api/ad-library/ai-context`；本文件規劃「把這份脈絡交給模型分析並呈現給使用者」。

## 背景與目標

使用者希望用 AI 模型分析整條「行銷活動 → 廣告組合 → 廣告 → 文案／素材」的脈絡，回答例如：

- 這個行銷活動的結構（預算層級、受眾切法、最佳化目標）有沒有明顯問題？
- 同一廣告組合內的素材測試、文案測試，哪個版本比較好？樣本夠不夠下結論？
- 動態素材廣告裡，哪幾段文案、哪幾張圖表現最好？
- 下一步該加碼哪些文案／素材、該測什麼？

## 現況：可沿用的 AI 基礎建設

| 項目 | 現況 | 本功能的用法 |
|---|---|---|
| AI 供應商 | `modules/ai_hub`：實際只走 OpenRouter（`router.py` 會把 legacy 值一律視為 openrouter），預設模型 `deepseek/deepseek-v4-flash` | 沿用 |
| API Key | 每位使用者在設定頁自行填入，Fernet 加密存於 `TokenManager`（`get_ai_api_key`／`get_ai_settings`） | 沿用使用者自己的 Key 與模型設定，不另外管理金鑰 |
| Prompt | `AIService.analyze_data` 依 `report_type` 分支各自的 system prompt，共用 `markdown_format_spec` | 新增 `report_type="ad_library_campaign"` 分支 |
| 串流 | `StreamingResponse`（text/plain）逐段回傳 Markdown | 沿用 |
| 前端呈現 | `ReactMarkdown`（`AnalyticsAiInsightCard.jsx`、`ContributionAiInsights.jsx` 等） | 沿用同樣的渲染方式 |
| 快照 | fb_ads 有 `fb_ads_analytics_ai_snapshots`（docs/58） | 參考其做法另建本模組的表 |

## 建議決策（2026-10-14 已確認，照建議實作）

1. **後端專用端點，伺服器端組脈絡**（建議）
   - 新增 `POST /api/ad-library/ai-analysis`，由後端呼叫 `ai_context.build_campaign_context` 組好脈絡再丟給模型，前端只送 `account_id`、`campaign_id`。
   - 不採用「前端先抓 `/ai-context` 再送到通用的 `/api/ai/analyze`」：那樣脈絡會在網路上來回兩次，而且送給模型的資料由前端決定、可被竄改；伺服器端組裝可確保只分析有權限的帳號資料。
2. **分析單位：單一行銷活動**（建議第一版只做這個）
   - 與 `/ai-context` 一致，資料量可控。帳號層級總覽（跨行銷活動比較）留到第二版。
3. **權限：沿用 `ad_library` 模組權限，不新增細項權限**（建議）
   - 呼叫的是使用者自己的 AI Key、自己付費，與 fb_ads 的 `fb_ads:ai:use` 不同；若之後改用團隊共用 Key，再加細項權限控管。
   - 使用者未設定 AI Key 時回 400，前端引導到設定頁。
4. **保存分析結果**（建議）
   - 新表 `ad_library_ai_analyses`：保存每次分析的 Markdown、使用的模型、脈絡雜湊與建立時間。
   - 打開同一行銷活動時先顯示最近一次結果，不用每次重新付費；資料重新抓取後（脈絡雜湊改變）提示「資料已更新，可重新分析」。

## 技術方向

### 後端

**`POST /api/ad-library/ai-analysis`**（`require_ad_library_module`，帳號 403／行銷活動 404 同 `/ai-context`）

- Request：`{account_id, campaign_id, model?}`；`model` 省略時用使用者設定。
- 流程：授權 → `ensure_contents` → `load_campaign_bundle` → `build_campaign_context` → 計算脈絡雜湊 → 串流呼叫模型 → 串流結束後寫入 `ad_library_ai_analyses`。
- 注意 2026-07-08、2026-08-07 連線池事故的慣例：組好脈絡後**先釋放 DB session**再開始串流；串流結束寫入結果時另開短 session。

**`GET /api/ad-library/ai-analysis?account_id=&campaign_id=`**：最近一次結果（含 `context_hash` 是否與目前資料相符）。

**脈絡大小控制**

- `/ai-context` 已限制每個行銷活動最多 300 則廣告。送模型前再估算字數（中文約 1 字 ≈ 1 token 的保守估計），超過上限（預設約 6 萬字元）時依花費由低到高刪去廣告，並在 `notes` 註明。
- 預估成本：50 則廣告的行銷活動約 1～2 萬 token 輸入；以預設 DeepSeek 模型計算費用很低，但使用者若改用較貴的模型，前端在送出前顯示「預估輸入字數」。

**System prompt 要點**（`AIService` 新增 `ad_library_campaign` 分支）

- 角色：資深 Meta 廣告投手，向行銷主管報告。
- 硬性規則：
  - 只引用 payload 內的數字，禁止編造；以 `P1`、`I2` 等代號提到文案／素材時，必須同時引用該段文案的前幾個字，讓人看得懂。
  - 成效歸屬：一般廣告的文案測試／素材測試只能說「在其他條件相同下，這個版本的廣告表現較好」，不能說「這段文案的 CTR 是 X%」；只有 `asset_results`（動態素材元件成效）可以直接歸給元件。
  - 樣本量：曝光低於 1,000 的版本不下勝負結論，明說「樣本不足」。
  - 行銷活動範圍的比較橫跨不同受眾，差異可能來自受眾或預算，需提醒。
  - `settings_available=false` 的節點不推論其設定。
  - 繁體中文、台灣用語；沿用 `markdown_format_spec`。
- 輸出分節：
  1. `## 📌 重點摘要`（3～5 點）
  2. `## 結構檢視`（預算層級、受眾切法、最佳化目標與目標是否一致）
  3. `## 文案與素材測試`（逐組結論，表格呈現）
  4. `## 動態素材元件表現`（有 `asset_results` 才出現）
  5. `## 建議下一步`（加碼哪些、暫停哪些、下一輪測什麼）

### 資料表（新增 alembic migration）

**`ad_library_ai_analyses`**

| 欄位 | 說明 |
|---|---|
| `id` | `alai_` + uuid |
| `account_id`, `campaign_id` | index (`account_id`, `campaign_id`, `created_at`) |
| `requested_by` | FK `users.id` |
| `model` | 實際使用的模型 |
| `context_hash` | 脈絡 JSON 的 sha256（判斷資料是否已更新） |
| `context_chars` | 送出的脈絡字數（成本追蹤） |
| `content` | Markdown 結果 |
| `status` | `succeeded` / `failed`（串流中斷時存已收到的部分並標 failed） |
| `created_at` | |

### 前端

- 「結構」分頁的行銷活動節點加「AI 分析」按鈕；「比對」分頁的範圍選單旁也加入口（選擇行銷活動後分析）。
- 點擊後開側邊面板：
  - 有舊結果 → 顯示結果、分析時間、模型；資料已更新時顯示提示與「重新分析」按鈕。
  - 沒有結果 → 顯示預估輸入字數、目前模型，按「開始分析」後串流顯示。
  - 未設定 AI Key → 引導到設定頁的 OpenRouter 分頁。
- Markdown 渲染沿用 `ReactMarkdown` + `remark-gfm`。

## 風險與待確認

- **模型幻覺**：已以「只引用 payload 數字」「代號需附原文」等規則降低；上線初期需人工抽查幾份分析。
- **使用者模型選擇**：較弱或較貴的模型都可能被選；prompt 需在 DeepSeek 預設模型上驗證過再上線。
- **費用**：由使用者自己的 OpenRouter Key 支付；畫面上需清楚顯示「會使用你的 AI Key」。
- **資料時效**：分析的是最近一次抓取的快照，面板需顯示資料抓取時間。

## 第 6 步：正式環境試跑（2026-10-15）

以 `nvidia/nemotron-3-ultra-550b-a55b:free` 分析「WK 69 NEW 2C 轉換 CBO2」（9 個廣告組合、34 則廣告，脈絡約 2.9 萬字元）：

- 有遵守的規則：五段結構、代號附原文、曝光不足 1,000 標「樣本不足」、跨廣告組合比較時提醒受眾與預算不同。
- 發現的問題與修正（尚未部署）：
  1. 拿文案與素材**都不同**的廣告互相比較（例如 P4+H4+I2 對 P3+H3+V1），並下結論「圖文版 CTR 近雙倍於影片版」——差異來源無法判斷。prompt 新增規則 7a：勝負結論只能來自 `comparisons[]` 與 `asset_results`，其餘只能並列描述並註明無法判斷差異來源。
  2. 推論用語過於肯定（「極高機率重疊」）。新增規則 7b：推論一律用保留語氣。
  3. 面板中表格的數字被從中間斷開（例如「19,7／99」），原因是整個內容區套了 `overflow-wrap: anywhere`。改為只在段落與清單允許任意斷行，表格放進可橫向捲動的容器。
- prompt 調整後需再試跑一次確認 7a／7b 有被遵守。
