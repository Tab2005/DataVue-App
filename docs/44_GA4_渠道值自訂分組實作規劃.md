# 44_GA4 渠道值自訂分組實作規劃

## 背景

延續 [[43_GA4_渠道值自訂分組擴充構想]] 定案的設計：到達頁分頁的渠道篩選再加一層「自訂分組」下拉，讓使用者能把多個原始渠道值（例如 `facebook / post-ads`、`facebook / cpc`）用自訂規則歸到同一個分組（例如「Facebook 付費廣告」）一起篩選，同時保留付費/自然的區隔（不像直接改選「來源」維度那樣把所有 Facebook 流量混在一起）。本文件把定案的設計拆成可依序執行的實作步驟。

## 現況程式碼位置

- 到達頁渠道篩選（前一階段成果）：`backend/modules/ga4/insights/landing_pages.py`（`get_landing_pages` 已支援 `channel_dimension`/`channel_value` 單一精確值篩選）
- GA4 查詢底層：`backend/modules/ga4/service.py`（`GA4AnalyticsService.get_analytics`，目前 `dimension_filter: Tuple[str, str] | None` 只能做「單一維度＋單一精確值」的 `Filter.StringFilter(EXACT)`）
- 既有分類規則前例：`GA4LandingPageRule`/`GA4ItemCategoryRule`（`backend/database/models/ga4_insights.py`），CRUD 端點在 `backend/modules/ga4/insights_router.py` 的 `landing-page-rules`/`item-category-rules`
- 前端分類規則管理面板前例：`frontend/src/components/GA4Insights/LandingPagesTab.jsx` 的「分類規則」收合面板（`landingRulesOpen` 那段）

## 關鍵設計決策（承接 43 號定案）

- 三個獨立下拉：維度／渠道值（原始值）／自訂分組，「渠道值」跟「自訂分組」互斥（只能選一個當篩選條件）
- 規則衝突依 `priority` 排序取第一個比對成功的，不允許重疊
- 規則綁定單一維度，不跨維度共用
- 新增規則後自動出現在對應維度的「自訂分組」下拉裡，不用另外維護選單

## 關鍵技術點：GA4Service 要能篩「多個值的 OR 組合」

42 號做的 `dimension_filter: Tuple[str, str]` 只能組出 `Filter.StringFilter(match_type=EXACT)` 這種單一精確值篩選。自訂分組需要把一個分組底下**所有符合的規則**（可能不只一條，例如「Facebook 付費廣告」可能同時有 `pattern="facebook / cpc"` 精確比對、也有 `pattern="facebook / post"` prefix 比對）各自轉成一個 `Filter.StringFilter`（EXACT/BEGINS_WITH/CONTAINS 對應 exact/prefix/contains），再用 `FilterExpression.or_group`（`FilterExpressionList`）組合成一個查詢送出去。

`get_analytics` 的 `dimension_filter` 參數要擴充成能接受兩種形狀（向下相容 42 號的呼叫方式）：
- `Tuple[str, str]`（維度, 精確值）→ 沿用現有的 EXACT 單一比對邏輯，不改行為
- `List[Tuple[str, str, str]]`（每個元素是 (維度, match_type, pattern)）→ 組成 `or_group`

## 實作步驟（依序執行）

### 步驟 1：後端模型 + migration
- 檔案：`backend/database/models/ga4_insights.py`
- 新增 `GA4ChannelGroupRule`：`id`、`property_id`、`channel_dimension`（String，比照 `ChannelDimension` 白名單值）、`group_label`（String，自由文字）、`match_type`（String：`prefix`/`contains`/`exact`，比到達頁規則多一個 `exact` 選項，因為自訂分組常見情境是先精確排除幾個已知例外值）、`pattern`、`priority`、`created_by`、`created_at`、`updated_at`
- 新 alembic migration，比照 `20260710_ga4_landing_page_rules.py` 的 `_table_exists`/inspector 寫法

### 步驟 2：後端 repository + CRUD service
- 檔案：`backend/modules/ga4/repository.py`：`create_channel_group_rule`、`list_channel_group_rules(property_id, channel_dimension=None)`、`get_channel_group_rule`、`delete_channel_group_rule`
- 新檔 `backend/modules/ga4/insights/channel_groups.py`：`list_channel_group_rules`、`upsert_channel_group_rule`（id 有值更新、無值新增，同到達頁規則語意）、`delete_channel_group_rule`；另外一個 `list_channel_groups(db, property_id, channel_dimension)` 依 `group_label` 去重回傳分組清單（供前端下拉用，不用另開端點以外的東西，直接從規則列表 derive）
- 掛進 `insights/__init__.py` 的 `GA4InsightsService` facade

### 步驟 3：GA4Service 擴充成支援 OR 組合篩選
- 檔案：`backend/modules/ga4/service.py`
- `_build_dimension_filter_expression` 改寫：判斷 `dimension_filter` 是 2-tuple（沿用現有 EXACT 邏輯）還是 list（組 `or_group`）
- match_type 對應：`exact` → `Filter.StringFilter.MatchType.EXACT`、`prefix` → `BEGINS_WITH`、`contains` → `CONTAINS`
- 快取鍵已經是把整個 `dimension_filter` 序列化進去（42 號做的），list 形狀一樣能正確序列化，不用再改

### 步驟 4：到達頁查詢邏輯支援 channel_group
- 檔案：`backend/modules/ga4/insights/landing_pages.py`
- `get_landing_pages` 新增 `channel_group: str | None` 參數，跟 `channel_value` **互斥**（兩者都給要回 `ValueError`）；`channel_group` 有值時 `channel_dimension` 必填
- 邏輯：用 `channel_dimension` + `channel_group` 查出所有符合的 `GA4ChannelGroupRule`，找不到規則（分組不存在或已被刪除）要回 `ValueError`；把規則轉成 `List[Tuple[dimension, match_type, pattern]]` 傳給 `dimension_filter`
- `kind` 命名比照 42 號的雜湊做法：`landing_page:{key_event}:chg_{hash(channel_dimension:group:channel_group)}`（用不同前綴 `chg_` 跟精確值篩選的 `ch_` 區分，避免同一個 property 剛好雜湊碰撞混淆，雖然機率極低但前綴區分更清楚好排查）
- payload 新增 `channel_group` 欄位供前端顯示

### 步驟 5：API 端點
- 檔案：`backend/modules/ga4/insights_router.py`
- `GET /landing-pages` 新增 `channel_group: str | None = Query(None, max_length=100)`
- 新增規則 CRUD 端點，比照 `landing-page-rules` 的寫法：`GET/PUT/DELETE /channel-group-rules`（`GET` 支援 `property_id` + 可選 `channel_dimension` 篩選）
- 驗證：`channel_value`/`channel_group` 兩者都給要回 400；`channel_group` 有值但 `channel_dimension` 沒給要回 400

### 步驟 6：前端 API client
- 檔案：`frontend/src/services/ga4InsightsService.js`
- `getLandingPages` 再加 `channelGroup` 參數
- 新增 `listChannelGroupRules`、`upsertChannelGroupRule`、`deleteChannelGroupRule`

### 步驟 7：前端規則管理 UI
- 檔案：`frontend/src/components/GA4Insights/LandingPagesTab.jsx`
- 新增「渠道分組規則」收合面板，比照現有「分類規則」面板：需要先選「維度」下拉（規則綁定單一維度），列出該維度下的規則（分組名稱／比對方式／pattern／優先序），可新增/刪除
- 表單：分組名稱（自由文字輸入）、比對方式（exact/prefix/contains）、pattern、優先序

### 步驟 8：前端「自訂分組」下拉 + 互斥邏輯
- 檔案：`frontend/src/components/GA4Insights/LandingPagesTab.jsx`、`frontend/src/pages/GA4Insights.jsx`
- 選了「維度」後，除了現有的「渠道值」下拉，再抓一次該維度的分組規則（步驟 2 的 `list_channel_groups`），組出「自訂分組」下拉選項
- 互斥邏輯：選了「渠道值」要清空「自訂分組」，選了「自訂分組」要清空「渠道值」，兩個下拉的 onChange 都要清空對方的 state 再觸發查詢

### 步驟 9：測試
- 後端：`GA4Service` 的 OR 組合 filter 組建（多個 pattern 各自轉成正確的 `Filter.StringFilter`，用 `or_group` 包起來）
- 後端：`get_landing_pages` 帶 `channel_group` 時查到規則、組出正確篩選、`channel_value`/`channel_group` 互斥驗證、找不到分組時報錯
- 後端：規則 CRUD 端點（create/list/delete，比照 `test_ga4_landing_page_rules.py` 的測試風格）
- 前端維持手動驗證，同 42 號的既有慣例

### 步驟 10：GA4 API 相容性人工驗證（不可省略）
- 用真實 GA4 property 測試 `or_group` 篩選出來的加總數字，是否等於「把每個原始值分別篩一次再加總」的結果（理論上應該完全一致，但要實測確認 GA4 沒有奇怪的去重/口徑差異，尤其 `sessionKeyEventRate` 這類去重比率指標在多值 OR 篩選下的分母定義）

## 不在本次範圍內

- 不做分組規則跨維度共用
- 不處理一個原始值同時屬於多個分組的情境（依優先序取第一個）
- 不做「自訂分組」下拉跟「渠道值」下拉的合併呈現（維持三個獨立下拉）
