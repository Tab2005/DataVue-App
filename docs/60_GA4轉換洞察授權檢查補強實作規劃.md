## 1. 問題重述

`require_ga4_insights_view` / `require_ga4_insights_manage_alerts` 只回答「這個人能不能用洞察功能」，不回答「這筆資料是不是他的」。

洞察模組的端點可分成兩類：

| 類型 | 例子 | 是否有隱性授權門檻 |
|---|---|---|
| 查詢類 | `/dashboard`、`/landing-pages`、`/items`、`/channels` | **有**——一律用呼叫者自己的 GA4 OAuth 憑證（`user.ga4_access_token`）打 Data API，讀不到的 property 直接錯誤 |
| 本地資料表讀寫類 | `/snapshots/{id}/ai-summary`、`/snapshots/{id}/share`、各類規則、KPI 目標 | **沒有**——純本地 CRUD，只看 id |

第二類就是 docs/59 P0-2 / P0-3 指出的 IDOR：任何一個有洞察檢視權限的登入使用者，只要拿到（或猜到）別人的 `snapshot_id` / `rule_id`，就能

- 改寫別人快照的 AI 解讀
- **替別人的快照開一個公開分享連結**（`GET /share/{token}` 無需登入，等同把別的屬性的 GA4 數據對外發佈）
- 改寫、刪除別人的分類規則／渠道分組規則／KPI 目標
- 透過 `upsert` 直接覆寫 `row.property_id`，把一條規則**搬到自己的屬性底下**

## 2. 授權模型的選擇

docs/59 給了兩個方向：「比對 `fetched_by`」或「比對該使用者可存取的 `property_id` 清單」。本次採用**後者（屬性層級）**，理由：

1. **`fetched_by` 會被覆寫。** `upsert_snapshot` 每次都會把 `fetched_by` 設成最後一個載入的人。同團隊兩人都接了自己的 GA4 到同一個 property 時，A 載入 → B 載入 → A 就存不了 AI 解讀了。用 `fetched_by` 當擁有者會製造新的功能缺陷。
2. **規則類的讀取本來就是屬性範圍。** `list_landing_page_rules(property_id=...)` 不分建立者，UI 也是列出該屬性的全部規則。讀取是屬性範圍、寫入卻是建立者範圍的話，會出現「看得到卻改不動」——所以授權邊界本來就該是屬性。

（告警規則 `anomaly_rules` 維持既有的 `created_by` 比對不動：它的 `list_rules` 本來就是 `created_by` 範圍，讀寫邊界一致。）

### 「可存取的屬性」怎麼判斷

GA4 沒有本地的「使用者 ↔ 屬性」對照表，憑證是 per-user OAuth。因此用兩段式，先快後慢：

1. **快路徑（本地）**：本地快照表有沒有 `property_id == P 且 fetched_by == 我` 的列。
   快照列**只會在 Data API 查詢成功後才寫入**（各查詢都是 `if error: raise RuntimeError(error)` 在 upsert 之前），而憑證是 per-user，所以這筆列本身就是「我自己的 Google 帳號讀得到 P」的證據。實務上使用者一定先載入某個分頁才會去存解讀或編規則，絕大多數請求在這裡就結束，**不需要任何對外呼叫**。
2. **慢路徑（Admin API）**：冷啟動時問 `GA4Client.list_properties`。結果快取 5 分鐘（`_PROPERTY_LIST_CACHE_TTL`），因為它是 `list_accounts` + 每個 account 一次 `list_properties`，而洞察頁載入時多支清單請求幾乎同時發出。**查詢失敗不寫入快取**，避免一次暫時性錯誤把使用者鎖在門外整個 TTL；失敗一律保守拒絕（同 contribution `resolve_accessible_account_ids` 的慣例）。

> 注意快路徑刻意比對 `fetched_by`，而不是「這個 property 有沒有快照」——後者等於任何人只要別人抓過就通行。

### 狀態碼

沿用 contribution 模組（docs/27 任務 1.3）已經確立的同一套慣例：

- **`property_id` 是顯式 query/body 參數的端點 → 403**，訊息帶 property id（呼叫者本來就知道自己傳了什麼，不構成探測管道）
- **資源 id 是路徑參數的端點 → 404**，且訊息與「查無此資源」**逐字相同**，讓「不存在」與「不是你的」無法從回應區分

## 3. 實作內容

### 3.1 `backend/modules/ga4/repository.py`

新增 `user_has_fetched_property(db, *, user_id, property_id) -> bool`（快路徑的 EXISTS 查詢）。

### 3.2 `backend/modules/ga4/dependencies.py`

新增授權層（與 contribution 把授權放在 `dependencies.py` 的位置一致）：

| 函式 | 用途 |
|---|---|
| `has_ga4_property_access(db, *, user, property_id)` | 兩段式判斷的核心，其餘都是它的包裝 |
| `_accessible_property_ids(user, db)` | 慢路徑＋快取；回傳 `None` 代表查詢失敗（與「清單為空」區分） |
| `verify_ga4_property_access_or_403(db, *, user, property_id)` | 顯式 property_id 的端點用 |
| `require_ga4_resource_access_or_404(db, *, user, resource, resource_id)` | 資源 id 的端點用；查列＋檢查＋回傳該列，未授權/不存在同一個 404 |

`_GA4_RESOURCE_LOOKUPS` 把 5 種資源（snapshot / 到達頁規則 / 商品分類規則 / 渠道分組規則 / KPI 目標）對映到各自的 repository 取用函式與 404 訊息，避免五份幾乎相同的 helper。

### 3.3 `backend/modules/ga4/insights_router.py`

| 端點 | 新增檢查 |
|---|---|
| `PUT /snapshots/{id}/ai-summary` | 資源 404 |
| `POST /snapshots/{id}/share` | 資源 404 |
| `GET /landing-page-rules`、`/item-category-rules`、`/channel-group-rules`、`/channel-groups`、`/kpi-targets` | property 403 |
| `PUT /landing-page-rules`、`/item-category-rules`、`/channel-group-rules` | payload property 403 ＋（帶 id 時）既有列 404 ＋ 換綁 400 |
| `PUT /kpi-targets` | payload property 403 |
| `DELETE` 三類規則、`/kpi-targets/{id}` | 資源 404 |

清單類端點（`GET`）原本也是純本地讀取、只吃 `property_id`，同樣會外洩他人的規則與 KPI 目標，所以一併納入——雖然 docs/59 的 P0-3 只點名了 upsert/delete。

新增的 router 內部 helper `_verify_rule_not_moved_across_properties` 同時處理兩件事：既有列的屬性必須可存取（404），且必須與請求帶的 `property_id` 相同（400）。原本 `upsert_*_rule` 會直接 `row.property_id = property_id`，即使兩邊都有權限，那也不是「更新規則」該有的語意。

### 3.4 刻意不改的部分

- **`GET /share/{token}` 維持公開**：這是分享功能的本體，設計如此。
- **`POST /anomaly-rules` 不加屬性檢查**：告警規則排程執行時用的是**建立者自己的**憑證（`evaluate_rule` 以 `rule.created_by` 撈 user），對別人的屬性建規則只會得到失敗的查詢，讀不到任何資料；且 update/delete 已有 `created_by` 比對、list 已是 `created_by` 範圍。屬於另一個層次的問題，不在本次範圍。
- **查詢類端點不加檢查**：已有 per-user OAuth 的隱性門檻，多加一層只是重複成本。

## 4. 測試

新增 `backend/tests/test_ga4_insights_authorization.py`（20 個測試）：

1. `has_ga4_property_access` 本身：快路徑不打 Admin API、別人抓的快照不算數、慢路徑查清單、Admin API 失敗保守拒絕、清單有快取、失敗不進快取
2. 快照類：改寫他人 AI 解讀回 404 且**內容未變**、替他人快照開分享連結回 404 且 **`share_token` 仍為 None**、自己的快照仍可正常操作（走快路徑）
3. 規則類：更新/刪除他人屬性的規則回 403/404 且資料未變、跨屬性換綁回 400、三類規則與 KPI 目標的刪除各自覆蓋
4. 清單類：四支清單端點對他人屬性回 403

`conftest.py` 新增 `ga4_property_access` fixture：把慢路徑換成固定清單，**只授予 `"123456"`**（GA4 測試通用的 property id），因此 `"999999"` 在所有測試中一律代表「別人的屬性」，可以直接當攻擊情境使用。既有 8 個端點測試掛上這個 fixture 即通過，未改動任何斷言。
