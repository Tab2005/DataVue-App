# GA4 查詢並行化實作規劃（docs/59 P1-2）

- 立案日期：2026-08-04
- 對應審查項目：docs/59 §P1-2「GA4 API 呼叫全部循序執行」（建議處理順序 7）

---

## 1. 問題

各洞察模組一次載入會循序打出多支彼此無資料相依的 GA4 查詢：

| 模組 | 查詢數 | 循序鏈 |
|---|---|---|
| `items.py` | 5–6 | 主查詢 →（相容性 fallback）→ 近 7 天 → 前 7 天 → 比較期間 → 分類拆解 |
| `item_landing_cross.py` | 3–6 | 商品指標 →（fallback）→ 商品×到達頁對照 → 到達頁指標 → 商品比較 → 到達頁比較 |
| `landing_pages.py` | 2–3 | 主查詢 → 關鍵事件拆解 → 比較期間 |
| `channels.py` | 2 | 工作階段維度 → 首次接觸維度 |
| `dashboard.py` | 2 | 當日 hour×渠道 → 當日 hour×事件 |

冷快取的首次載入就是這些 round-trip 相加。L1（10 秒）/L2（Redis 120 秒）雙層
快取只救得了重複載入，救不了第一次。

## 2. 真正的難點：執行緒安全

docs/59 建議用 `ThreadPoolExecutor` 包住獨立查詢。直接這樣做會踩到一個不明顯
但很嚴重的問題——`GA4Service.get_analytics` 目前吃 `user` 與 `db`：

```python
creds = GA4Client.get_credentials(user, db)   # service.py:78
```

而 `get_credentials` 在 token 快過期時會：

```python
creds.refresh(GoogleAuthRequest())
if db:
    user.ga4_access_token = creds.token
    user.ga4_expires_at = ...
    db.commit()                                # client.py
```

把這段丟進多個 worker thread 同時跑會有三個問題：

1. SQLAlchemy `Session` **不是 thread-safe**，多執行緒共用同一個 Session 是未定義行為
2. worker thread 裡的 `db.commit()` 會把**整個請求 Session 當下所有待寫入的東西**
   一起 commit，包含呼叫端還沒打算送出的變更
3. `db.commit()` 之後（`expire_on_commit=True`）ORM 物件的屬性會過期，下一次讀
   `user.ga4_access_token` 會觸發 SELECT——多執行緒同時觸發就是在共用 Session 上
   同時發查詢
4. 就算沒有 commit，N 個 worker 各自判斷 token 需要刷新，會打出 N 次 refresh

**解法：讓 worker thread 完全碰不到 `user` 和 `db`。**

在請求執行緒先把憑證解析好（該刷新的刷新、該回寫的回寫，就這一次），再把
`Credentials` 物件傳給並行的查詢：

```python
credentials = resolve_ga4_credentials(user, db)   # 請求執行緒，只有這裡碰 db
results = run_parallel({
    "main":      lambda: GA4Service.get_analytics(..., credentials=credentials),
    "breakdown": lambda: GA4Service.get_analytics(..., credentials=credentials),
})
```

`get_analytics` 收到 `credentials` 就跳過 `get_credentials`，因此 worker thread
上的呼叫路徑不含任何 Session 存取。這是結構性的保證，不是「小心不要碰」的約定。

快取層（`cache.py`）本身已經有 `_l1_lock` 保護，不需要額外處理。

## 3. 相依關係與分階段

並行的前提是查詢之間沒有資料相依。逐支確認後：

| 模組 | 第 1 階段（並行） | 第 2 階段 | 相依理由 |
|---|---|---|---|
| `channels.py` | 工作階段維度、首次接觸維度 | — | 無 |
| `dashboard.py` | 主查詢、事件拆解 | — | 無 |
| `landing_pages.py` | 主查詢、關鍵事件拆解、比較期間 | — | 比較期間的指標在發查詢前就已決定 |
| `items.py` | 主查詢鏈、近 7 天、前 7 天、分類拆解 | 比較期間 | 比較期間要用主查詢的 fallback 結果決定指標 |
| `item_landing_cross.py` | 商品指標鏈、商品×到達頁對照、到達頁指標、到達頁比較 | 商品比較 | 同上 |

「主查詢鏈」指「官方比率指標 →（失敗才）退回基礎指標」這一段——它本身有相依，
所以整段當成**一個** task 丟進去，鏈內仍然循序。

`items.py` / `item_landing_cross.py` 的比較查詢**可以**用官方指標樂觀發出去、
真的 fallback 時再重發一次，換到單一階段。不做：省下的是一個 round-trip，換來
一條在 fallback 情境下白打一次 API（吃配額）且難以測試涵蓋的路徑。兩階段已經把
5–6 次 round-trip 壓到 2 次。

## 4. 行為變化（刻意接受的）

主查詢失敗時，現在是「主查詢 raise → 後面的查詢根本不會發」；並行後同階段的
其他查詢已經送出去了，然後才 raise。代價是失敗情境多打 2-3 次 API（且多半會命中
快取），換來成功情境（絕大多數）的延遲下降。不接受這個代價就沒有並行的空間。

日誌與 mock 的呼叫順序不再固定。既有測試若斷言 `captured_calls[0]` 是哪一支，
要改成順序無關的寫法——斷言的本意是「主查詢的 group by 只有 landingPage」，
不是「主查詢排第一」。

## 5. 執行緒池

模組層級單一 `ThreadPoolExecutor`，worker 數由 `GA4_INSIGHTS_MAX_PARALLEL_QUERIES`
控制（預設 8）。理由：

- 每次請求現開 pool 在高並發下會爆執行緒；共用 pool 的上限就是保護
- 這些 task 彼此不互等，pool 滿了只會退化成排隊（＝現在的循序行為），不會死鎖
- 端點本來就是同步 `def`、跑在 FastAPI 的 threadpool 上，我們的 pool 不巢狀在自己裡面

只有一個 task 時直接在當前執行緒跑，不進 pool。

## 6. 測試

新增 `backend/tests/test_ga4_parallel_queries.py`：

1. `run_parallel` 真的並行（用 barrier/latch 驗證，循序執行會 timeout）
2. task 拋例外時往外傳，不會被吞掉
3. 只有一個 task 時不進 pool
4. **並行的查詢完全不碰 `db`**：傳一個一被碰到就爆炸的假 Session，跑完整條
   `get_items` / `get_landing_pages`，確認只有請求執行緒碰過它
5. `credentials` 有傳時 `get_analytics` 不呼叫 `get_credentials`
6. 各模組並行後 payload 內容與循序版本一致（既有測試已涵蓋大部分，這裡補
   「同一份 mock 資料，並行前後結果相同」的鎖）

## 7. 不做的事

- 不把整條鏈改寫成 async（`google-analytics-data` 的同步 client 要換成 async
  client，範圍遠大於本項）
- 不動 `kpi.py` / `anomaly_rules.py` 的迴圈查詢：那是 N 個目標各一次查詢，
  並行化的收益與風險評估跟本項不同，另案。`anomaly_rules.py` 的取樣迴圈跟
  儀表板基線是同一個形狀，日後要處理可以直接照抄本次的做法
- 不動快取策略

## 8. 完成紀錄（2026-08-04）

### 追加範圍：儀表板基線取樣

實作時發現 docs/59 的呼叫點統計漏了一區。`dashboard.py` 表面上只有 2 支
`GA4Service.get_analytics`，但 `_compute_metric_baseline` 底下還有一層：

```
一次刷新的基線組數 = 1（全部關鍵事件）+ 最多 5（個別事件）+ 2（非轉換指標）= 8
每組取樣日 = 8 週
→ 最壞 64 次循序 GA4 查詢
```

這些查詢藏在 `_shared.py` 的 `_fetch_metric_total` 底下，所以用「數 get_analytics
出現次數」的方式看不到。這是整個洞察模組最大的循序鏈，比原本列出的五個模組
加起來還多，已一併並行化（每組基線的 8 個取樣日一次送出）。

刻意**不**把 8 組基線也並行——那會變成 `run_parallel` 巢狀在 `run_parallel` 裡，
外層 task 佔滿共用 pool 並等待永遠排不到 worker 的內層 task，是典型的執行緒池
死鎖。只並行內層就有 8 倍改善，且沒有巢狀。

### 循序 → 並行的 round-trip 數

| 模組 | 之前 | 之後 |
|---|---|---|
| `channels.py` | 2 | 1 |
| `dashboard.py`（主體） | 2 | 1 |
| `landing_pages.py` | 2–3 | 1 |
| `items.py` | 5–6 | 2 |
| `item_landing_cross.py` | 3–6 | 2 |
| `dashboard.py`（基線） | 最壞 64 | 最壞 8 |

### 突變測試

刻意破壞六處，**六個突變全部被抓到**：

| 突變 | 失敗測試數 |
|---|---|
| `run_parallel` 改回循序執行 | 3 |
| `run_parallel` 吞掉 task 例外 | 2 |
| `get_analytics` 忽略外部傳入的 `credentials`（回到每支查詢各自查憑證） | 1 |
| 到達頁的並行查詢把 `db` 帶進 worker | 1 |
| 基線取樣改用完成順序而非日期順序 | 2 |
| 單一取樣失敗不再容錯 | 1 |

其中「把 `db` 帶進 worker」那一個，正是這次最想防住的迴歸——測試用一個
「被非請求執行緒碰到就記錄下來」的假 Session 釘住它。
