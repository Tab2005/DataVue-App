# 59_GA4 轉換洞察模組架構審查報告

審查日期：2026-07-31
審查範圍：`backend/modules/ga4/`（3,993 行）＋ `frontend/src/components/GA4Insights/`、`GA4Insights.jsx`、`SharedGA4Insight.jsx`、`ga4InsightsService.js`（4,837 行），合計約 8,800 行
基準狀態：GA4 相關測試 180 個全數通過（`pytest tests/test_ga4_*.py`）

---

## 摘要

這個模組的**資料正確性設計是這份程式碼最強的部分**——口徑決策（pp vs 成長率、同分類比較、固定配對）都有文件與註解佐證，容錯策略一致（輔助查詢失敗只記警告、錯誤欄位分開標示，不會把「查詢失敗」誤標成「這是新項目」），注入防護紮實（維度白名單、事件名正規表達式、刻意不開放 regex 避免 ReDoS）。

問題集中在**三個面向**：

1. **分享連結的資料生命週期有實際缺陷**——已分享出去的連結，內容會在使用者重新載入分頁時被靜默改寫，AI 解讀還會直接消失（已實測確認）
2. **授權檢查不一致**——告警規則有做擁有者驗證，但快照與分類規則類端點沒有，形成 IDOR 風險
3. **前端狀態管理已達規模上限**——單一元件 93 個 `useState`、單一分頁 53 個 props，加上四份重複的 `GrowthBadge`

以下依嚴重度排列。

## P0-1：重新載入分頁會清空已分享出去的 AI 解讀，且分享內容會靜默變動

**嚴重度：高（對外可見、影響客戶信任）** — **已於 2026-07-31 修復，見 docs/61**

### 問題

`repository.upsert_snapshot()`（`backend/modules/ga4/repository.py:22-50`）在找到同一組 `(property_id, kind, date)` 的既有列時，會覆寫 `payload`、並把 `ai_summary` / `ai_summary_generated_at` 重設為 `None`——但**不會動 `share_token`**。

而 `GET /landing-pages`、`/items`、`/channels` 等端點**每次呼叫都會重新查 GA4 並 upsert**（`insights_router.py:205-233`），沒有「已有今日快照就直接回傳」的短路邏輯。

兩者相加的結果是：

```
使用者開啟到達頁分頁          → 建立快照
產生 AI 解讀                  → ai_summary 寫入
產生分享連結、寄給客戶        → share_token 建立
使用者當天再次開啟同一個分頁  → upsert 覆寫 payload、ai_summary 被清成 None
客戶此時打開連結              → 連結有效，但解讀是空的，數字也跟寄出時不同
```

### 實測佐證

以臨時測試腳本直接驅動 repository 層（測試後已刪除），輸出：

```
--- 分享連結在使用者重新載入分頁後的狀態 ---
token 仍有效: True
ai_summary: None          ← 客戶看到空白解讀
payload 數字: 137          ← 寄出時是 100，已靜默變成 137
```

### 影響

- 客戶收到的連結打開後看不到 AI 解讀（最常見情境：早上分享、下午自己再看一次分頁就壞了）
- 更隱蔽的問題是**數字會變**：分享出去的「快照」實際上不是快照，是一個會跟著動的即時視圖。討論時雙方看到的數字可能不同
- 使用者無從察覺，因為連結本身仍然有效、頁面也正常渲染

### 建議修法

推薦**在產生分享連結的當下複製一份不可變副本**，而不是讓分享連結指向會被覆寫的工作快照。這與 docs/58 剛為成效分析頁確立的模式一致（「每次點解讀都建立全新快照，分享連結一旦產生就永久凍結」），兩個模組的語意也就統一了。

具體做法：`create_share_link()` 改成把來源列的 `payload` + `ai_summary` 複製成一筆新列（例如 `kind` 加 `:shared` 後綴或另立資料表），`share_token` 掛在副本上。既有的 `get_snapshot_by_share_token` 不用改。

次佳解（改動更小、但語意較弱）：`upsert_snapshot` 在偵測到 `row.share_token` 非空時，不覆寫該列而是另開新列。

## P0-2：快照類端點缺少擁有者驗證（IDOR）

**嚴重度：高（跨租戶資料外洩）** — **已於 2026-07-31 修復，見 docs/60**

### 問題

`PUT /snapshots/{snapshot_id}/ai-summary`（`insights_router.py:468-482`）與 `POST /snapshots/{snapshot_id}/share`（`insights_router.py:486-499`）只掛了 `require_ga4_module` + `require_ga4_insights_view` 這兩個**通用**權限，**完全沒有驗證這個 `snapshot_id` 是否屬於呼叫者**。

服務層也沒補：`sharing.py:9` 與 `kpi.py:8` 都是直接把 `snapshot_id` 丟給 repository，中間沒有任何 `fetched_by == user.id` 之類的檢查。

### 影響

任何一個有 GA4 洞察檢視權限的登入使用者，只要拿到（或猜到）別人的 `snapshot_id`，就可以：

- **改寫**別人快照的 AI 解讀內容
- **替別人的快照開一個公開分享連結**——`GET /share/{token}` 是無需登入的公開端點，等同把別的租戶的 GA4 數據對外發佈

`snapshot_id` 格式是 `gis_{uuid4().hex[:12]}`（48 bits），不算容易窮舉，但 ID 不可猜測不能當作授權機制。

### 對比：同模組已有正確做法

值得注意的是，**告警規則的端點做對了**（`anomaly_rules.py:17-32, 45-49`）：

```python
def update_rule(db, *, rule_id: str, user_id: str, payload: dict):
    row = repository.get_rule(db, rule_id)
    if not row or row.created_by != user_id:   # ← 有擋
        return None
```

所以這不是「團隊沒有這個概念」，而是**同一套模式沒有一致套用**。

### 建議修法

在 `save_ai_summary` / `create_share_link` 加上與 `update_rule` 相同的擁有者檢查（比對 `fetched_by`，或改成比對該使用者可存取的 `property_id` 清單），查無權限一律回 404（不要回 403，避免洩漏該 ID 是否存在）。

## P0-3：分類規則類端點同樣缺少擁有者/屬性驗證

**嚴重度：中高** — **已於 2026-07-31 修復，見 docs/60**（一併涵蓋原本未點名的清單類 `GET` 端點）

`upsert_landing_page_rule`（`landing_pages.py:252-276`）、`delete_landing_page_rule`、以及對應的商品分類規則、渠道分組規則，都是拿 `rule_id` 直接讀出來就改/刪：

```python
if rule_id:
    row = repository.get_landing_page_rule(db, rule_id)
    if not row:
        return None
    row.property_id = property_id    # ← 沒有檢查原本的 property_id 是誰的
    row.category = category
```

不只沒有驗證擁有者，`upsert` 還允許呼叫者**把別人的規則搬到自己的 property 底下**（直接覆寫 `row.property_id`）。

建議：比照 P0-2，統一補上擁有者檢查；`upsert` 時若 `rule_id` 已存在且 `property_id` 與請求不符，應視為錯誤而非默默改綁。

## P1-2：GA4 API 呼叫全部循序執行

**嚴重度：中（使用者體感延遲）**

各模組的 GA4 查詢次數（`GA4Service.get_analytics` 呼叫點）：

| 模組 | 呼叫點數 |
|---|---|
| `items.py` | 6 |
| `item_landing_cross.py` | 6 |
| `landing_pages.py` | 3 |
| `channels.py` / `dashboard.py` | 2 |

以商品分頁為例，一次載入最多會**循序**打出：主查詢 →（相容性 fallback 重試）→ 近 7 天 → 前 7 天 → 比較期間 → 分類拆解。這些查詢彼此無資料相依，卻是一個接一個 `await` 完的。

有兩點緩解因素，所以評為 P1 而非 P0：
- `GA4AnalyticsService.get_analytics` 有 L1（記憶體 10 秒）+ L2（Redis 120 秒）雙層快取，重複載入很快
- 端點是同步 `def`，FastAPI 會丟到 threadpool，不會卡住 event loop

但**冷快取的首次載入**（使用者切到商品分頁、或改了篩選條件）就是 5-6 個 round-trip 相加，體感明顯。

**建議**：把無相依的查詢改成並行。由於底層是同步呼叫，較低風險的做法是用 `concurrent.futures.ThreadPoolExecutor` 包住那幾支彼此獨立的查詢，而不是把整條鏈改寫成 async。

## P1-3：分享連結無法撤銷、無期限、無存取紀錄

**嚴重度：中（安全治理）** — **撤銷已於 2026-07-31 補上，見 docs/63**（`expires_at` 與存取紀錄依原文「可視需求排期」，仍待辦）

`share_token` 一旦產生就永久有效：
- 沒有 revoke 端點（`insights_router.py` 只有 create 與 read）
- 沒有 `expires_at` 欄位
- 沒有存取記錄，無法知道連結被誰看過幾次

對一個「把 GA4 數據公開給未登入者」的功能來說，這三項缺一都算是治理缺口。誤發給錯的人之後沒有任何補救手段。

**建議**：至少補 `DELETE /snapshots/{id}/share`（把 token 設回 NULL）；`expires_at` 可視需求排期。

## P2-1：前端狀態管理已達單一元件規模上限

**嚴重度：中（可維護性）**

`GA4Insights.jsx` 是 1,206 行、**93 個 `useState`** 的單一元件，往下傳的 props 數量：

| 分頁 | props 數 |
|---|---|
| `ItemsTab` | **53** |
| `LandingPagesTab` | **51** |
| `AlertsTab` | 23 |
| 其餘 4 個分頁 | 11-12 |

到達頁與商品這兩個分頁各自要接 50+ 個 props，實務上的後果是：
- 每次加一個小功能（例如這次的 `totalItems`、`eventsTotal`）都要在三處同步改動：父層 state、傳遞、子層解構
- 任何一個 state 變動都會 re-render 整個 1,206 行元件與全部 7 個分頁（沒有 `memo`）
- 已經開始出現漏傳的類別（AlertsTab 的 `eventsTotal` 需要新增一條 state 專門承接後端早就回傳但前端沒用的 `total` 欄位）

**建議**（可漸進，不必一次到位）：把到達頁與商品各自的一整組狀態抽成 custom hook（例如 `useLandingPagesTab(propertyId)`），讓分頁元件自己持有狀態，父層只傳 `propertyId` 與共用的 `language`/`t`。這兩個分頁抽完就能消掉 100 個 props 中的絕大多數。

## P2-3：分享頁的表格是完全獨立的第二套實作

**嚴重度：中（已兩度造成缺漏）**

`SharedGA4Insight.jsx`（514 行）裡的 `LandingPagesTable` / `ItemsTable` / `ItemLandingCrossTable` 與各分頁元件的表格是**兩套獨立程式碼**，欄位、格式化、成長標示都得手動保持同步。

這個結構已經實際造成兩次缺漏：
- docs/54：比較欄位做完後，分享頁完全沒顯示，使用者回報才補
- docs/56：因為記取教訓才在同一輪主動補上——**靠的是人記得，不是靠結構保證**

只要這兩套還是分開的，第三次漏掉只是時間問題。

**建議**：把表格主體抽成同時被兩邊引用的 presentational 元件（吃 `rows` + `payload`，不含篩選/分頁邏輯）。這比 P2-1 的改動小，收益明確。

## P2-4：測試用的反射 hack 洩漏進正式程式碼

**嚴重度：低（技術債）**

`_shared.py:118-132` 有三個函式透過 `sys.modules` 在執行期反查 facade 屬性：

```python
def _service_attr(name: str, fallback):
    facade = sys.modules.get("modules.ga4.insights_service")
    service = getattr(facade, "GA4InsightsService", None) if facade is not None else None
    return getattr(service, name, fallback)
```

呼叫端如 `landing_pages.py:56`、`:138`：

```python
start_date, end_date = _service_attr("_trailing_period", _trailing_period)(days)
category = _facade_attr("classify_landing_page", classify_landing_page)(landing_page, rules)
```

這個間接層存在的唯一理由是讓測試能 monkey-patch facade 上的同名屬性。代價是正式路徑上每次呼叫都多一次 `sys.modules` 查表 + 兩次 `getattr`，而且讓「這裡到底會執行哪個函式」變得無法從程式碼靜態判讀。

**建議**：測試改為直接 patch 定義處（`mocker.patch("modules.ga4.insights.landing_pages.classify_landing_page")`），然後移除這三個 helper。屬於低風險的清理，但要連動改測試，可排在功能開發的空檔。

## P2-5：`__all__` 通配匯出污染命名空間

**嚴重度：低**

`_shared.py:249` 與 `insights/__init__.py:113` 都是：

```python
__all__ = [name for name in globals() if not name.startswith("__")]
```

這會把 `asyncio`、`logging`、`os`、`re`、`smtplib`、`sys`、`datetime`、`median`、`User`、`GA4Service` 等**所有 import 進來的東西**一併匯出。各子模組再 `from ._shared import *`，等於每個檔案的命名空間都被塞滿無關符號，靜態分析工具也無法判斷未使用的 import。

**建議**：改成明確列出要匯出的名稱。屬於一次性清理。

## P2-6：前端分頁未做 code splitting

**嚴重度：低**

`GA4Insights.jsx` 一次性 import 全部 7 個分頁元件，打包後 `GA4Insights` chunk 為 **83.83 kB**（gzip 19.14 kB），是所有頁面 chunk 中最大的。使用者只看總覽分頁也要載入告警、KPI、商品頁面比對的全部程式碼。

專案在 `App.jsx` 已經有成熟的 `lazy()` 慣例，套用到分頁層級是同一套做法。

**建議**：優先把最少被開啟、體積最大的分頁（商品、到達頁）改為 `lazy()`。

## 值得保留的設計（不建議在重構時改掉）

審查過程中確認了幾項刻意且正確的決策，這裡記錄下來，避免日後被誤當成不一致而「修正」：

1. **輔助查詢的容錯粒度**——每支輔助查詢失敗都只記警告、不擋主表格，且錯誤欄位各自獨立（`compare_query_error` / `item_compare_query_error` / `landing_compare_query_error` / `category_breakdown_error`）。這讓前端能精準提示「哪一部分暫缺」，而不是整頁失敗
2. **`kind` 後綴設計**——`:{key_event}`、`:ch_{hash}`、`:chg_{hash}`、`:cmp` 讓不同篩選/模式的快照與其 AI 解讀互不覆寫；用雜湊而非原始字串是為了避開 `String(80)` 長度上限與截斷碰撞，考慮得很完整
3. **比率型指標用百分點（pp）而非成長率**——避免「5%→6%」被講成「成長 20%」，且 UI 有 tooltip 解釋
4. **docs/56 的固定配對決策**——比較上一期時沿用本期算出的「商品→主要到達頁」對應，不重新判定。這避免了跨期比較時悄悄換掉被測對象，是這次審查中看到最細緻的一個判斷（但**目前沒有測試保護**，見 P1-1）
5. **注入防護**——`CHANNEL_DIMENSION_MAP` 白名單、`LANDING_PAGE_KEY_EVENT_PATTERN` 正規表達式、分類規則刻意不支援 regex（避免 ReDoS），三處都有明確註解說明理由
6. **同分類內比較「高流量低轉換」**——文章頁天生低轉換，混排會讓商品頁的問題頁被稀釋，這個語意變更是對的
