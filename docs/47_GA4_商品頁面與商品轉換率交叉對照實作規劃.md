# 47_GA4 商品頁面與商品轉換率交叉對照實作規劃

## 背景

延續 [[40_GA4_商品頁面與商品轉換率交叉對照擴充構想]] 記錄的缺口：「到達頁」分頁（以頁面為單位）跟「商品」分頁（以商品本身為單位）互相獨立，沒有地方能同時看到「這個商品」跟「這個商品主要的到達頁」兩邊的轉換表現放在一起比較。本文件把構想文件結尾留下的三個待確認問題拍板，拆成可依序執行的實作步驟。

## 三個待確認問題拍板

### 1. 合併視圖放哪裡 → 獨立新分頁

不塞進既有的到達頁或商品分頁（兩邊維度單位不同，硬塞會讓現有表格語意混亂），新增一個獨立分頁，暫定命名「商品頁面比對」（英文 `Item × Landing Page`），插在「商品」分頁之後。

### 2. 資料串接方式 → 應用層合併三支查詢，不做單一雙維度比率查詢

構想文件裡提到兩個選項：(a) `itemName` + `landingPage` 雙維度單一查詢，或 (b) 應用層合併既有的兩支查詢。拍板用 **(b) 的變形**，具體是三支查詢：

1. **商品指標查詢**（沿用 `items.py` 現有的官方比率/容錯 fallback 邏輯）：`dimensions=["itemName"]`，取 `purchaseToViewRate`/`cartToViewRate`/`itemsViewed`
2. **商品↔到達頁對照查詢**（新增，但沿用 `items.py` 裡 `itemName × itemCategory` 已經驗證可行的同一套模式）：`dimensions=["itemName", "landingPage"]`，`metrics=["itemsViewed"]`——**刻意只用純計數指標，不用比率指標**，同商品對應到多個到達頁時取瀏覽量最高者當「主要到達頁」（tie-break邏輯完全比照 `classify` 主分類那段）
3. **到達頁指標查詢**（沿用 `landing_pages.py` 現有查詢形狀）：`dimensions=["landingPage"]`，`metrics=["sessions", "sessionKeyEventRate", "bounceRate"]`

**為什麼不做 (a) 單一雙維度比率查詢**：`sessionKeyEventRate`/`purchaseToViewRate` 這類比率指標在 GA4 Data API 對維度組合的相容性限制比計數指標嚴格（`items.py` 現有的 `ITEM_METRICS_FALLBACK` 容錯邏輯就是在處理類似的相容性問題），直接把兩個比率指標塞進同一個雙維度查詢，相容性風險完全不可控。改成三支查詢後，唯一的新查詢（第 2 支）只用計數指標 `itemsViewed`，跟現有 `itemName × itemCategory × itemsViewed` 已經在生產環境驗證過的組合是同一種形狀，相容性風險大幅降低——不用賭一個沒試過的比率指標組合能不能過。

合併邏輯（應用層 Python）：對每個商品，用第 2 支查詢查出主要到達頁，再用第 3 支查詢查出這個到達頁的 `sessions`/`session_key_event_rate`/`bounceRate`，兩邊數字放進同一列。查不到對照到達頁（例如該商品瀏覽量為 0，或對照查詢失敗）時該商品這幾欄留空，不擋主表格（同 `items.py` 現有 `category_breakdown_error` 的容錯慣例）。

### 3. 呈現方式 → 每列一個商品，帶「主要到達頁」+ 差異標記

- **一個商品對應多個到達頁時**：只取瀏覽量最高的一個當「主要到達頁」呈現（不在表格裡同時列出全部到達頁），跟現有「商品主要分類」的解法一致，維持 MVP 簡單、之後有需要再擴充成可展開清單
- **表格欄位**：商品名稱、主要到達頁（URL，過長截斷+ hover 顯示完整）、商品瀏覽後購買率、到達頁轉換率（`session_key_event_rate`）、到達頁工作階段數、差異標記
- **差異標記**（呼應構想文件的動機範例）：`page_underperforms_item`——當「到達頁轉換率」落在後 25 百分位、但「商品瀏覽後購買率」不在後 25 百分位時標記，代表「頁面可能有設計/載入速度問題，而非商品本身不吸引人」；沿用到達頁分頁既有的百分位判定慣例（樣本數 <4 不標記）。本次只做這個方向的標記，「商品拖累頁面」的反向標記留待之後有需要再加（見下方不在本次範圍）

## 實作步驟（依序執行）

### 步驟 1：後端資料串接函式
- 新檔案 `backend/modules/ga4/insights/item_landing_cross.py`
- `get_item_landing_cross(db, *, user, property_id, days=7)`：依序執行上述三支查詢、應用層合併、計算差異標記
- 商品指標查詢的官方/fallback 容錯邏輯直接複製 `items.py` 現有寫法（重複約 10 行程式碼，換取不動到 `items.py` 既有已測試邏輯的風險）
- payload 包含 `items`（每個商品一列，含上述所有欄位）、`mapping_query_error`/`landing_query_error`（比照既有容錯欄位慣例）
- snapshot：`kind="item_landing_cross"`

### 步驟 2：facade 掛載
- `backend/modules/ga4/insights/__init__.py` 加 `get_item_landing_cross` staticmethod（比照其他既有函式的掛法）

### 步驟 3：API 端點
- `backend/modules/ga4/insights_router.py` 新增 `GET /item-landing-cross`（`property_id`、`days` 兩個參數，比照 `items` 端點）

### 步驟 4：前端 API client
- `frontend/src/services/ga4InsightsService.js` 新增 `getItemLandingCross(propertyId, days)`

### 步驟 5：前端新分頁
- 新檔案 `frontend/src/components/GA4Insights/ItemLandingCrossTab.jsx`
- `frontend/src/pages/GA4Insights.jsx`：`tabs` 陣列加入新分頁項目、新增對應 state（`itemLandingDays`/`itemLandingSnapshot`/`itemLandingLoading`/`itemLandingError`）與 `loadItemLandingCross`
- 沿用共用 `DaySelector`（含 [[46_GA4_自訂天數與AI解讀渠道範圍實作紀錄]] 剛加的自訂天數）

### 步驟 6：AI 白話解讀
- `backend/ai_service.py` 的 `ga4_insights` 分支 `kind_focus` 加一個 `"item_landing_cross"` 選項，重點放在「差異標記」的商品該優先檢查頁面還是商品本身
- 前端沿用共用 `<AIInsightNote>` 元件，`kind="item_landing_cross"`

### 步驟 7：測試
- 後端：mapping 查詢的主要到達頁判定（tie-break）、應用層合併正確性、差異標記的百分位判定（含樣本數 <4 不標記）、查詢失敗的容錯欄位
- 端點層：基本回應契約測試

### 步驟 8：GA4 API 相容性人工驗證（不可省略）
- 主要風險點：第 2 支查詢（`itemName` + `landingPage` + `itemsViewed`）雖然形狀跟現有 `itemName × itemCategory` 相同、預期相容性風險低，但仍需要接真實 GA4 property 實測確認不會回 400
- 驗證「主要到達頁」判定結果是否符合直覺（人工挑幾個商品，比對 GA4 介面上的實際到達頁分布）

## 不在本次範圍內

- 一個商品對應多個到達頁時的完整清單呈現（僅取主要到達頁，見上方拍板）
- 「商品拖累頁面」反向差異標記
- 渠道篩選（`channel_dimension`/`channel_value`/`channel_group`）——之後若有需要，可比照到達頁/商品分頁的做法擴充，本次先聚焦商品×到達頁的核心交叉對照
