# 50_GA4 當日總覽轉換事件拆分下拉選單實作規劃

## 背景

延續 [[49_GA4_當日總覽轉換事件拆分下拉選單擴充構想]] 拍板的 4 個決策，本文件把設計拆成可依序執行的實作步驟。

## 拍板決策（承接 49 號）

1. 「轉換」卡片預設顯示「全部關鍵事件」（維持現況總和口徑）
2. 下拉選單多列出**最多 5 個**依當日次數排序的個別關鍵事件，「全部關鍵事件」跟每個列出的個別事件都各自算基線、各自判斷異常
3. 事件清單靠 GA4 `eventName` 維度自動偵測，不寫死白名單
4. 只做「當日總覽」的「轉換」卡片，不擴充到「渠道對照」分頁
5. 採方案 B（一次刷新時全部算好存進 payload），下拉切換不重打後端 API；基線查詢量從現在 24 次增加到最多 64 次（有界，不隨屬性關鍵事件數量無限增加）

## 實作步驟（依序執行）

### 步驟 1：後端資料串接

- 檔案：`backend/modules/ga4/insights/dashboard.py::_fetch_intraday_dashboard_payload`
- 新增一支查詢（跟主查詢同一天）：`dimensions=["hour", "eventName"]`，`metrics=["keyEvents"]`——比照 `landing_pages.py` 的 `key_events_breakdown` 查詢形狀
- 依 `eventName` 加總當日總次數排序，取前 5 大當作「個別事件」清單；「全部關鍵事件」固定排第一位
- 對「全部關鍵事件」（`api_metric="keyEvents"`）與每個列出的個別事件（`api_metric=f"keyEvents:{event_name}"`），各自：
  - 用這支新查詢的資料組出 hourly 累計數字（依 `current_hour` 累加，同現有邏輯）
  - 呼叫既有的 `_fetch_metric_total(..., by_hour=True)` 抓 8 週歷史基線、算 `is_anomaly`（同現有 `sessions`/`purchaseRevenue` 的算法，只是 `api_metric` 換成 `keyEvents`/`keyEvents:{event}`）
- payload 新增：
  - `conversion_events`：有序清單 `[{"key": "__all__", "label": "全部關鍵事件"}, {"key": "purchase", "label": "purchase"}, ...]`
  - `conversions_by_event`：`{ "__all__": {cumulative_value, baseline, is_anomaly, hourly_totals}, "purchase": {...}, ... }`
- **向下相容**：既有的 `cumulative_totals.conversions`/`baseline.conversions`/`is_anomaly.conversions`/`hourly_totals[].conversions` 這幾個既有欄位維持不變（數字上等於 `conversions_by_event.__all__` 的對應值），避免影響 AI 白話解讀（`kind="intraday_hourly"`）等既有讀取這些欄位的地方
- 新查詢失敗時（例如該屬性沒有任何關鍵事件資料）`conversion_events` 只保留 `__all__`，不擋主要的 `cumulative_totals`/`baseline` 邏輯

### 步驟 2：前端下拉選單

- 檔案：`frontend/src/components/GA4Insights/GA4InsightsShared.jsx::IntradayMetricCard`
- 僅 `metricKey === 'conversions'` 時，卡片標題旁（ⓘ 提示旁邊）加一個下拉選單，選項來自 `payload.conversion_events`
- 元件內部 local state 記錄目前選中的 event key（預設 `__all__`），卡片顯示的累計數字/平常區間/是否異常/長條圖，改讀 `conversions_by_event[selectedKey]` 而非目前寫死的 `cumulativeValue`/`baseline`/`isAnomaly`/`hourlyTotals` props——**切換下拉選單純粹是前端本地狀態切換，不重新呼叫後端 API**
- `sessions`/`purchaseRevenue` 兩張卡片不受影響（沒有下拉選單，維持現況 props 介面）

### 步驟 3：測試

- 後端：事件排序取前 5 大、事件數不足 5 個時的邊界、「全部關鍵事件」跟個別事件基線各自獨立判定、新查詢失敗時的容錯（`conversion_events` 退回只有 `__all__`）、既有 `cumulative_totals.conversions` 等欄位數值不變（向下相容）
- 前端：`vite build` 編譯驗證（下拉選單邏輯屬於單純狀態切換，UI 手動驗證）

### 步驟 4：GA4 API 相容性人工驗證（不可省略）

- 確認 `dimensions=["hour", "eventName"]` + `metrics=["keyEvents"]` 這支新查詢對真實 GA4 property 能正常回應
- 確認排序取出的前 5 大事件符合直覺（人工比對 GA4 後台的事件報表）
- 確認 `keyEvents:{event_name}` 動態指標對這個屬性實際存在的事件名稱都能正確查到基線（事件名稱可能含特殊字元，需留意動態指標語法的邊界情況）

## 不在本次範圍內

- 「渠道對照」分頁的轉換相關指標拆分（見 49 號拍板第 4 點）
- 事件數量上限的動態調整（暫定寫死 5，之後如果需要可調整）
- `sessions`/`purchaseRevenue` 這兩張卡片的下拉選單（本次只做「轉換」卡片）
