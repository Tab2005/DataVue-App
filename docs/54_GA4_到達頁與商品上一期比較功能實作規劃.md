# 54_GA4 到達頁與商品上一期比較功能實作規劃

## 背景

使用者想在到達頁分頁加一個「跟上一期比較」的開關：右上角選 7/14/30 天時，開關打開後表格數字要能對照「往前推同樣天數的前一段期間」（例如選 7 天，就是這 7 天 vs 再往前的 7 天）。同一套功能也要沿用到商品分頁。

**技術上這不是新機制**：`items.py` 的「近 7 天/前 7 天瀏覽成長比較」（`views_growth_rate`）本來就是「查兩次同一組指標、日期範圍不同、用 `itemName` 對應算成長率」的做法。這次要做的，是把同一套機制從「寫死 7 天、跟上方期間選擇無關」改成「跟著使用者選的天數走、可開關」，先補到目前完全沒有這個功能的到達頁，商品那邊則是在既有固定 7 天成長指標之外，另外加這個可跟著天數走的版本。

## 拍板決策

1. **比較指標範圍**：全部欄位都比——到達頁是工作階段/轉換次數/轉換率/跳出率，商品是瀏覽數/加購率/購買率/營收
2. **開關預設狀態**：關閉（不主動多打一次 GA4 查詢）
3. **與商品既有「近7天/前7天」固定成長指標的關係**：並存，不取代——既有指標維持現況（固定 7 天、不受渠道篩選影響，語意是「全店這商品是不是在成長」），這次新加的是「跟著上方天數/渠道篩選走」的另一組比較資料
4. **新頁面/新商品（上一期完全沒有資料）**：不算成長率（分母為 0 沒有意義），顯示「🆕 新」標記

## 實作前需要跟你確認的兩個技術判斷（我先抓合理預設，你可以否決）

1. **自訂天數要不要一起支援**：技術上「往前推 N 天」這個機制對 7/14/30/自訂輸入的任何天數都一樣，沒有做不到的問題。既然全部欄位都要比、開關預設關閉（不會平白增加查詢量），我這次**預設一併支援自訂天數**，不特別排除——如果你還是想先只開放 7/14/30，跟我說一聲就好。
2. **「轉換率」「跳出率」這種比率型指標，比較方式要用「相對成長率」還是「百分點差異」**：工作階段、轉換次數這種「次數」型指標，比較用相對成長率（例如 ▲12%）很直覺；但轉換率/跳出率本身已經是比例，如果轉換率從 5% 變 6%，說「成長 20%」容易讓人誤解成長很多，我打算比照這類指標的慣例，改成**直接顯示百分點差異**（例如 +0.9 個百分點、-0.9 個百分點）。次數類指標維持相對成長率。這點我會在表格加上 ⓘ 說明清楚兩種算法的差異，避免使用者混淆。

## 技術方向

### 資料面（後端）

- `get_landing_pages()` / `get_items()` 都新增 `compare: bool = False` 參數
- `compare=True` 時，多查一次「往前推同樣天數的前一段期間」（`prior_end = start_date 前一天`，`prior_start = prior_end 往前推 days-1 天`），指標/維度跟主查詢一樣（到達頁：`sessions`/`keyEvents`/`sessionKeyEventRate`/`bounceRate` × `landingPage`；商品：`itemsViewed`/`cartToViewRate`/`purchaseToViewRate`/`itemRevenue` × `itemName`），**沿用主查詢當下的渠道篩選條件**，確保比較的是「同一組篩選條件下的兩期」
- 用 `landingPage`/`itemName` 對應本期與上一期的資料，本期有、上一期沒有 → 標記 `is_new: true`，不算成長率；兩期都有 → 依上面「拍板需確認」第 2 點的規則算出成長率（次數類）或百分點差異（比率類）
- `compare=False`（預設）完全不受影響，不多查、不變動既有 payload 形狀——**向下相容**
- snapshot 的 `kind` 比照既有 `key_event`/渠道篩選的疊加後綴慣例，`compare=True` 時加上 `:cmp` 後綴，跟「不比較」的快照分開存，AI 解讀不會互相覆寫
- 這次完全沒有用到新的 GA4 指標或維度組合——查的東西跟主查詢一模一樣，只是日期範圍不同，不屬於「新查詢語法」，不需要走「GA4 API 相容性人工驗證」那個保留給全新查詢形狀的步驟；仍建議實作完後你用真實資料快速肉眼核對一次數字合理即可

### 畫面面（前端）

- 到達頁/商品分頁的期間選擇器（`DaySelector`）旁邊加一個「比較上一期」開關（checkbox 或 toggle），預設關閉；開啟時重新請求資料（帶 `compare=true`）
- 表格呈現：不新增獨立欄位（到達頁已經 7 欄，商品欄位也不少，全部指標都加一組「本期/上期/差異」三欄會爆版面）。開關開啟時，**在每個既有指標欄位的數字旁邊，加一個小字的成長標示**（例如「1,634 ▲12%」「2.6% +0.4pp」），沒有比較資料時就是現況顯示，維持一致的欄位結構
- 上一期完全沒資料的列（新頁面/新商品），成長標示位置改顯示「🆕 新」徽章
- AI 解讀：`contextLabel` 補上「已啟用上一期比較」的說明，`buildPayload()` 把比較後的欄位一併帶給 AI，讓 AI 白話解讀時能提到「相較上一期」的變化（呼應 docs/46 已經建立的「AI 要知道目前畫面上是什麼篩選狀態」精神）
- 分享連結：跟關鍵事件/渠道篩選一樣，`compare` 是會改變 snapshot 內容/`kind` 的後端層級參數，不是像 docs/53 分類篩選那種純前端二次篩選，所以**不需要額外處理**——分享當下抓到的就是「有沒有開比較」那份 snapshot，分享出去自然會保留這個狀態，跟現有 key_event/渠道篩選分享行為一致

## 實作步驟（依序執行）

### 步驟 1：後端到達頁——`get_landing_pages()` 支援 compare ✅ 已完成

- 新增 `compare` 參數、上一期查詢、`landingPage` 對應、成長率/百分點差異計算、`is_new` 標記
- `kind` 加 `:cmp` 後綴
- payload 新增每列的比較欄位（例如 `sessions_prior`/`sessions_growth_rate`、`session_key_event_rate_prior`/`session_key_event_rate_delta_pp`、`is_new`），並在 payload 層級標示 `compare_enabled`、比較期間的 `compare_start_date`/`compare_end_date`

### 步驟 2：後端商品——`get_items()` 支援 compare ✅ 已完成

- 同步驟 1 的做法，套用到商品的 4 個指標，**不動既有的 `views_growth_rate`/`views_recent_7d`/`views_prior_7d`**（固定 7 天、不受渠道篩選影響的既有指標維持原樣）
- `kind` 加 `:cmp` 後綴（若同時有渠道篩選 hash 後綴，順序比照既有慣例疊加）

### 步驟 3：路由與 service layer 串接 ✅ 已完成

- `insights_router.py` 的 `/landing-pages`、`/items` 端點加 `compare: bool = Query(False)` 參數
- `ga4InsightsService.js` 的 `getLandingPages`/`getItems` 加 `compare` 參數

### 步驟 4：前端到達頁——比較開關與表格呈現 ✅ 已完成

- `DaySelector` 旁加開關；`loadLandingPages` 呼叫帶上 `compare` 狀態
- 表格各欄位依 `compare_enabled`/`is_new` 顯示對應的成長標示或新標記
- `contextLabel`/`buildPayload` 反映比較狀態

### 步驟 5：前端商品——同步驟 4

- 商品分頁做一樣的事，並確認既有的「瀏覽成長」欄位不受影響、兩組指標並存顯示不衝突

### 步驟 6：測試

- 後端：compare 開/關的 payload 差異、`landingPage`/`itemName` 對應正確、新頁面/新商品標記 `is_new`、成長率與百分點差異算法各自正確、`kind` 後綴、既有行為（`compare=False`）不受影響的回歸測試
- 前端：`vite build` 編譯驗證；人工在瀏覽器確認開關切換、成長標示/新標記顯示正確、AI 解讀與分享連結反映比較狀態

## 不在本次範圍內

- KPI 目標、商品頁面比對、渠道對照、當日總覽——這幾個分頁目前沒有「跟上一期比較」的需求，暫不做
- 比較期間長度跟主期間脫鉤（例如「這 7 天跟去年同期比」）——這次只做「往前推同樣天數」這一種比較邏輯
