# 42_GA4 到達頁渠道篩選實作規劃

## 背景

延續 [[41_GA4_到達頁依流量管道拆分轉換率擴充構想]] 定案的方案 A：在到達頁分頁加兩層下拉選單（維度＋渠道值），選定後把該頁面的工作階段/轉換次數/轉換率/跳出率重新查詢成「只算這個渠道」的數字，列數不變、複用渠道對照既有的維度選項。本文件把定案的設計拆成可依序執行的實作步驟。

## 現況程式碼位置

- 到達頁查詢：`backend/modules/ga4/insights/landing_pages.py`（`get_landing_pages`，目前只帶 `landingPage` 單一維度）
- 渠道維度白名單／對照表：`backend/modules/ga4/insights/_shared.py`（`CHANNEL_DIMENSION_MAP`），`backend/modules/ga4/insights_router.py`（`ChannelDimension` Literal）
- 前端維度選項：`frontend/src/components/GA4Insights/GA4InsightsShared.jsx:279`（`CHANNEL_DIMENSION_OPTIONS`）
- GA4 查詢底層：`backend/modules/ga4/service.py`（`GA4AnalyticsService.get_analytics`，實際組 `RunReportRequest` 的地方）
- 快照模型：`backend/database/models/ga4_insights.py`（`GA4InsightsSnapshot`，唯一鍵 `property_id + kind + date`）

## 關鍵發現（規劃時確認、會影響工作量估計）

**GA4Service 目前完全不支援 dimension filter。** 查過 `modules/ga4/service.py`，三個組 `RunReportRequest` 的分支（不分維度／分頁／全量拉取）都只有 `dimensions`/`metrics`/`date_ranges`/`limit`/`offset`，沒有任何 filter 參數。這代表「渠道值篩選」不是加一個參數就好，是要新增 GA4 Data API 的 `FilterExpression`/`Filter.StringFilter` 支援。好消息是 GSC 模組（`backend/gsc_service.py` 的 `dimension_filters` 參數）已經有「server-side dimension filter」這個模式的前例可以參考設計形狀，但 GA4 跟 GSC 兩邊 API 的 filter 物件結構不同，不能直接複製程式碼，只能參考設計思路。

## 實作步驟（依序執行）

### 步驟 1：GA4Service 加上 dimension filter 支援
- 檔案：`backend/modules/ga4/service.py`
- `get_analytics` 新增可選參數（例如 `dimension_filter: tuple[str, str] | None`，代表 `(維度名, 篩選值)`）
- 三個 `RunReportRequest` 組建分支都要接上：用 `google.analytics.data_v1beta.types.FilterExpression` + `Filter` + `Filter.StringFilter`（`match_type=EXACT`）組出 `dimension_filter=` 參數
- 快取鍵（`generate_cache_key`）要把 filter 條件也編進去，否則不同渠道篩選會共用同一個快取結果、拿到錯的資料
- 對應往上兩層的 `ga4_service.py`/`GA4Service.get_analytics` 也要補上這個透傳參數

### 步驟 2：到達頁查詢邏輯加渠道篩選
- 檔案：`backend/modules/ga4/insights/landing_pages.py`
- `get_landing_pages` 新增參數 `channel_dimension: str | None`、`channel_value: str | None`（兩者必須同時有值或同時沒有，其中一個缺另一個要回錯）
- 有值時：取 `CHANNEL_DIMENSION_MAP[channel_dimension][0]`（工作階段那一半）當實際 GA4 維度名，主查詢的 `dimensions` 從 `["landingPage"]` 改成 `["landingPage", 該維度]`，並帶上步驟 1 做好的 `dimension_filter=(該維度, channel_value)`
- 關鍵事件分項查詢（`key_events_breakdown`，目前 `dimensions=["landingPage", "eventName"]`）也要一併加上同樣的渠道篩選，否則主表格數字有篩、分項明細數字沒篩，兩邊會對不起來
- `kind` 命名比照 `key_event` 已有的疊加規則，改成類似 `landing_page:{key_event}:{channel_dimension}:{channel_value}`（沒有篩選時維持原本命名，向下相容），確保不同渠道篩選各自存成獨立快照，AI 解讀/[[39_GA4_轉換洞察快照分享連結實作計劃|分享連結]]不會互相覆寫——這代表 39 號分享連結功能會自動對篩選後的結果生效，不用額外開發

### 步驟 3：API 端點加參數
- 檔案：`backend/modules/ga4/insights_router.py`
- `GET /landing-pages` 新增 `channel_dimension: ChannelDimension | None = Query(None)`、`channel_value: str | None = Query(None, max_length=100)`
- 驗證：兩者必須同時提供或同時不提供，否則回 400

### 步驟 4：前端 API client
- 檔案：`frontend/src/services/ga4InsightsService.js`
- `getLandingPages` 簽名加上 `channelDimension`、`channelValue`，帶進 query string

### 步驟 5：前端「渠道值」清單來源
- 不新增後端端點：渠道值清單直接復用既有 `getChannels(propertyId, days, dimension)` 回應裡的 `payload.channels[].channel`
- 到達頁分頁目前跟渠道對照分頁是各自獨立的 tab 狀態，沒有互相共用資料，需要在使用者選定「維度」後，用該維度呼叫一次 `getChannels` 取得該維度底下實際存在的渠道值，拿來組第二層下拉選單的選項（這次呼叫是額外新增的，跟渠道對照分頁原本各自的抓取互不影響）

### 步驟 6：前端 UI（到達頁分頁）
- 檔案：`frontend/src/components/GA4Insights/LandingPagesTab.jsx`、`frontend/src/pages/GA4Insights.jsx`
- 在既有「全部關鍵事件」下拉旁邊，加兩個下拉：
  1. 維度選單：直接複用 `CHANNEL_DIMENSION_OPTIONS`，預設「不篩選」
  2. 渠道值選單：選了維度後才啟用，選項來自步驟 5 抓到的清單，預設「全部渠道」（等同不篩選，維持現況）
- 選單變動時觸發 `loadLandingPages` 重新查詢，用法比照現有 `landingKeyEvent` 的狀態管理模式

### 步驟 7：測試
- 後端：`GA4Service.get_analytics` 的 filter 組建邏輯（mock GA4 client，驗證 `RunReportRequest` 有正確帶入 `dimension_filter`）
- 後端：`get_landing_pages` 帶渠道篩選時，`kind` 命名正確、與未篩選版本各自獨立存快照（比照既有 `test_ga4_landing_page_rules.py`／`test_ga4_channel_dimension.py` 的測試風格）
- 後端：只給 `channel_dimension` 不給 `channel_value`（或反過來）要回 400
- 前端：暫無自動化測試覆蓋此模組（既有 GA4Insights 前端測試也是空白），本次維持現況，以手動驗證為主

### 步驟 8：GA4 API 相容性人工驗證（不可省略）
- 實際接一個有資料的 GA4 property，確認 `landingPage` + 渠道維度 + `dimension_filter` 這個組合下，`sessionKeyEventRate`／`sessions`／`bounceRate` 這幾個指標算出來的數字，跟「只看該渠道」時的認知是否一致（例如拿 GA4 官方後台的探索報表交叉核對幾筆）
- 這步驟做完才能判斷步驟 1-6 的設計是否需要調整，建議排在步驟 1-2 完成、有一個可動的雛形之後就先做，不要等到全部做完再驗證

## 不在本次範圍內

- 不做「頁面 × 渠道」全展開的下鑽表格（已在 41 號文件定案捨棄）
- 不做多渠道同時勾選比較（一次只能篩一個渠道值）
- 不處理 40 號文件（商品頁面 × 商品交叉對照）的缺口，兩者分開評估
