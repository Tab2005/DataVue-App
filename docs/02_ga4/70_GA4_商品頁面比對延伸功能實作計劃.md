# 70_GA4 商品頁面比對延伸功能實作計劃

> 建立日期：2026-08-10
> 狀態：**待審閱，尚未拍板是否動工**——本文件僅供評估複雜度與工作量，三項功能皆未開始實作。

## 背景

[[47_GA4_商品頁面與商品轉換率交叉對照實作規劃]]（「商品頁面比對」分頁）步驟 1-8 已全部完成並驗收通過，但該文件「不在本次範圍內」明確排除了三項延伸功能，至今無後續文件跟進（見 [[69_全專案未完成規劃與缺口盤點]] 02_ga4 章節的盤點記錄）：

1. 「商品拖累頁面」反向差異標記
2. 渠道篩選
3. 一個商品對應多個到達頁時的完整清單呈現

本文件逐項評估這三項的技術方案、影響範圍與複雜度，供決定是否動工、以及動工順序之用。三項彼此獨立，可以只挑一項做，不需要一次全做。

## 複雜度總表

| # | 功能 | 複雜度 | 主要原因 | 粗估工作量 |
|---|---|---|---|---|
| 1 | 反向差異標記 | 低 | 沿用既有百分位計算，純邏輯反轉 | 數小時 |
| 2 | 渠道篩選 | 中 | 邏輯機械式可抄，但要動的檔案面廣（3-5 支查詢＋router＋前端＋分享頁） | 半天～一天 |

## 延伸功能一：「商品拖累頁面」反向差異標記

### 現況

`backend/modules/ga4/insights/item_landing_cross.py`（約第 204-216 行）已經算好兩邊指標的後 25 百分位（`page_rate_p25`、`item_rate_p25`），目前只用來判斷「頁面拖累商品」：

```python
row["page_underperforms_item"] = (
    row["page_session_key_event_rate"] <= page_rate_p25
    and row["purchase_to_view_rate"] > item_rate_p25
)
```

### 技術方案

在同一段迴圈裡，反向條件是既有邏輯的鏡射：

```python
row["item_underperforms_page"] = (
    row["purchase_to_view_rate"] <= item_rate_p25
    and row["page_session_key_event_rate"] > page_rate_p25
)
```

代表「商品瀏覽後購買率偏低，但到達頁本身的轉換率不低」——頁面把人帶進來、也有把其他商品轉換掉的能力，問題出在這個商品本身（素材、定價、庫存、商品頁文案等），而不是頁面。

### 影響範圍

- `backend/modules/ga4/insights/item_landing_cross.py`：新增一個布林欄位，計算邏輯緊鄰既有的 `page_underperforms_item`
- `backend/tests/test_ga4_item_landing_cross.py`：新增對應單元測試（比照既有 `page_underperforms_item` 的四分位判定測試，含樣本數 <4 不標記）
- `frontend/src/components/GA4Insights/ItemLandingCrossTab.jsx`：表格新增一個標記欄位/badge
- `frontend/src/pages/SharedGA4Insight.jsx` 的 `ItemLandingCrossTable`：同步補上這個欄位（**docs/47 已經在這裡踩過一次「新增欄位忘記同步分享頁」的坑，這次要特別注意**）
- `backend/modules/ai_hub/service.py` 的 `item_landing_cross` kind_focus：補一句解讀「反向標記」的白話說明，讓 AI 摘要能識別新欄位

### 風險

低。不新增查詢、不改變既有欄位，樣本數不足（<4）時的既有防呆邏輯直接沿用。

## 延伸功能二：渠道篩選

### 現況

`items.py`（商品分頁）與 `landing_pages.py`（到達頁分頁）已有一套驗證過的渠道篩選機制（docs/42+44+45），核心組成：

- `channel_dimension`（白名單：`default_channel_group`/`source_medium`/`source`/`medium`/`campaign`）+ `channel_value`（精確值）或 `channel_group`（自訂分組，多條件 OR）互斥
- 驗證規則：`channel_value` 與 `channel_group` 互斥；帶了任一個就必須帶 `channel_dimension`；`channel_dimension` 沒搭配任一個會報錯
- 依驗證結果組出 `dimension_filter`（單一 tuple 或 list-of-tuple 的 or-group 形狀），傳入每一支 `GA4Service.get_analytics()` 呼叫
- Snapshot 的 `kind` 用 hash 摘要加後綴區分快取（`channel_group` 用 `chg_` 前綴、精確值篩選用另一種 hash），避免不同篩選條件互相覆蓋同一筆快照

`item_landing_cross.py` 目前有 3 支查詢（不開比較期間）或最多 5 支（開比較期間：商品指標、商品×到達頁對照、到達頁指標、商品比較、到達頁比較）。

### 技術方案

1. `get_item_landing_cross()` 簽名加入 `channel_dimension`/`channel_value`/`channel_group` 三個參數，開頭複製 `items.py` 現成的驗證邏輯（互斥檢查、白名單檢查）
2. 依驗證結果算出 `dimension_filter`，傳入全部 3～5 支 `GA4Service.get_analytics()` 呼叫——**這裡要注意「商品×到達頁對照」查詢（`itemName × landingPage`）套用渠道篩選在語意上是合理的**（只看這個渠道帶來的商品瀏覽跟到達頁組合），但要留意跟「到達頁指標查詢」的篩選條件必須一致，避免兩邊篩選範圍對不上导致合併出錯誤配對
3. `insights_router.py` 的 `/item-landing-cross` 端點比照 `/items`、`/landing-pages` 端點加上三個 Query 參數
4. Snapshot `kind` 命名比照既有慣例加後綴，**且要跟 docs/56 已經在用的 `:cmp` 後綴共存**（例如 `item_landing_cross:cmp:chg_xxxx` 這種疊加後綴的形狀，需要設計清楚的組合順序規則，避免跟現有的 `item_landing_cross:cmp` 混淆）
5. 前端 `ItemLandingCrossTab.jsx` 加渠道篩選下拉（比照 `ChannelsTab.jsx`/`ItemsTab.jsx` 既有 UI）
6. `frontend/src/services/ga4InsightsService.js` 的 `getItemLandingCross()` 加三個參數
7. **`SharedGA4Insight.jsx` 的 `kindGroup()` 函式要特別檢查**：目前 `kind === 'item_landing_cross'` 是精確比對，`item_landing_cross:cmp`（docs/56 的比較期間後綴）並不會命中這個精確比對，會落到下面 `kind.startsWith('item')` 的分支、被誤判成「商品」分頁而非「商品頁面比對」分頁——這跟 docs/47「附帶修復」段落記錄過的那個坑是同一類問題，且目前看起來對 `:cmp` 後綴本身可能就還沒修好。渠道篩選會再疊加一種後綴形狀，動工前建議先把 `kindGroup()` 改成 `kind.startsWith('item_landing_cross')`（擺在 `item` 判斷之前）一次修好，涵蓋現有的 `:cmp` 與未來的渠道篩選後綴

### 影響範圍

後端：`item_landing_cross.py`、`insights_router.py`、對應測試（`test_ga4_item_landing_cross.py`）
前端：`ItemLandingCrossTab.jsx`、`ga4InsightsService.js`、`GA4Insights.jsx`（state 與 loader）、`SharedGA4Insight.jsx`

### 風險

中。邏輯是照抄現成模式，風險可控，但改動檔案數量多，且發現了一個可能已經存在的 `kindGroup()` 精確比對缺陷（見上），建議動工前先單獨確認 `item_landing_cross:cmp` 快照的分享連結現在是否正常顯示，若已經是壞的，這算是獨立於本延伸功能的既有 bug，可以視情況先單獨修掉或一併處理。

## 延伸功能三：多到達頁完整清單呈現

### 現況

`item_landing_cross.py` 的查詢 2（`itemName × landingPage`，`metrics=["itemsViewed"]`）本質上已經回傳「每個商品對應的所有到達頁」，但目前應用層合併只保留瀏覽量最高的一筆：

```python
if item_name not in best_views_by_item or views > best_views_by_item[item_name]:
    best_views_by_item[item_name] = views
    primary_landing_page_by_item[item_name] = landing_page
```

其餘到達頁的資料被直接捨棄。**後端不需要新增查詢**——資料早就在查詢 2 跟查詢 3（到達頁指標，已涵蓋全部到達頁）的回應裡，缺的只是「不要丟掉」跟「呈現方式」。

### 技術方案（含尚待拍板的設計問題）

1. 合併邏輯從「單一 `primary_landing_page: str`」改成「`landing_pages: list`，依瀏覽量由高到低排序」，每筆包含 `landing_page`/`views`/`sessions`/`session_key_event_rate`/`bounce_rate`，第一筆維持原本「主要到達頁」的語意（供既有的差異標記邏輯與只看單一頁的舊消費端相容）
2. **待拍板問題 A：差異標記要不要每個到達頁各自算一次？** 目前 `page_underperforms_item` 是拿商品跟「主要到達頁」比。改成清單後，理論上每個到達頁都可以各自跟商品比一次，但這樣一個商品可能同時有「主要到達頁正常、次要到達頁拖累」的情況，UI 要怎麼呈現需要先想清楚（例如：只在主要到達頁上顯示標記，次要到達頁不顯示；或是每筆到達頁旁邊各自顯示標記）
3. **待拍板問題 B：前端呈現型態**。目前是「一列一個商品」的簡單表格，改成清單後至少有三種做法：
   - (a) 展開列（點商品列展開一個子表格顯示全部到達頁）——互動成本較高但表格結構乾淨
   - (b) 巢狀表格（到達頁欄位本身塞一個 mini 表格）——不用額外互動，但欄位可能撐得很高、跟其他欄位對不齊
   - (c) 跳出視窗/side panel（點「查看全部到達頁」開一個 modal）——最不影響主表格排版，但多一次點擊
   本文件不預先拍板，需要在動工前另外討論決定
4. 資料量評估：多數商品應該只對應少數幾個到達頁（同商品通常只有 1-2 個主要入口），但不排除少數熱門商品有 5-10+ 個到達頁進站的情況，UI 設計要能撐住這種長尾情境（例如清單本身也要有筆數上限或可捲動）
5. `SharedGA4Insight.jsx` 的 `ItemLandingCrossTable` 要同步支援清單呈現，不能只改分頁裡的表格

### 影響範圍

後端：`item_landing_cross.py`（資料形狀變更，屬於破壞性變更——若前端沒同步改，舊的 `row.primary_landing_page` 存取方式會直接壞掉，需要前後端同一個 PR 內一起改完，不能分批上線）、對應測試
前端：`ItemLandingCrossTab.jsx`（需要新 UI 元件，視上方拍板結果新增子元件）、`SharedGA4Insight.jsx`

### 風險

高於前兩項。除了程式碼工作量本身，還牽涉兩個需要先討論拍板的產品/設計決策（差異標記語意、UI 呈現型態），在拍板之前不建議直接動工，否則容易做完又要因為設計方向不對而重做。

## 建議執行順序（若決定動工）

若三項都要做，建議依複雜度由低到高：**反向標記 → 渠道篩選 → 多到達頁清單**。前兩項沒有相依關係、可以任選其一單獨做；第三項因為有待拍板的設計問題，建議排在最後，且動工前先確認上方「待拍板問題 A/B」的答案。

## 不在本文件規劃範圍內

- 是否要在動工渠道篩選之前，先單獨排查/修復 `kindGroup()` 對 `item_landing_cross:cmp` 精確比對可能造成的分享連結顯示問題——這算是獨立於三項延伸功能之外的既有現況確認，本文件只負責點出風險，是否要提前處理由後續另外決定
- 多到達頁清單的 UI 具體視覺設計（展開列/巢狀表格/彈出視窗三選一）
