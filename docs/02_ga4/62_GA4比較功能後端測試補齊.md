### 固定配對測試的佈局

刻意做成陷阱：本期 P1 的主要到達頁是 `/a`（瀏覽 70 > `/b` 的 30），但**上一期 `/b` 的流量遠高於 `/a`**（5000 vs 100 sessions）。若實作改成「對上一期重新判定主要頁面」，就會拿 `/b` 來比，比較對象在兩期之間被悄悄換掉。測試斷言必須抓到 `/a` 的上一期數據（100 sessions / 8%）。

## 3. 驗證方式：突變測試

新測試通過本身不代表它守得住——所以對三個最關鍵的斷言各做了一次突變測試（改壞實作、確認測試會紅、再還原）：

| 突變 | 結果 |
|---|---|
| 把固定配對改成對上一期重新判定流量最高的頁面 | ❌ `assert 5000 == 100` — 抓到 |
| 比率型指標改用相對成長率而非百分點 | ❌ `assert 19.99999999999999 == 1.0` — 抓到 |
| 比較查詢失敗時仍標記 `is_new` | ❌ `assert True is False` — 抓到 |

第二項的失敗訊息正好就是 docs/54 當初要避免的那個情境本身：轉換率 5%→6% 被算成「成長 20%」。

三次突變後都用 `git checkout --` 還原，最終 `git status` 只剩新增的測試檔。

---

## 4. 測試技法

三支被測函式都會連續打多次 `GA4Service.get_analytics`（主查詢／分項查詢／比較查詢），比較查詢與主查詢的 `dimensions` 相同、只有日期範圍不同。因此 mock 用 `side_effect` 依 **`dimensions` + `start_date` 是否等於上一期起日** 分派假資料。

上一期日期由測試自己用 `_trailing_period()` 推導（`_expected_periods()`），與實作同一套邏輯，不寫死日期——否則測試會在跨日時壞掉。
