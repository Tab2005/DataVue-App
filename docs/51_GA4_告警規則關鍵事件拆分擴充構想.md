# 51_GA4 告警規則關鍵事件拆分擴充構想

## 背景

延續 [[48_GA4_當日總覽轉換指標口徑標示]] 與 [[50_GA4_當日總覽轉換事件拆分下拉選單實作規劃]]：當日總覽的「轉換」卡片已經能拆分成個別關鍵事件檢視。使用者在「告警設定」頁籤看到「轉換」規則後詢問：這裡是不是也一樣全部關鍵事件混在一起偵測？能不能也拆分？

## 現況（相關程式碼）

- 規則資料表 `GA4AnomalyRule`（`backend/database/models/ga4_insights.py:35-51`）：`metric_key` 只是自由字串，實際可用值靠 `SUPPORTED_METRICS = {"conversions": "conversions", "sessions": "sessions", "purchase_revenue": "purchaseRevenue"}`（`_shared.py`）決定，沒有事件層級的欄位。
- 評估邏輯 `evaluate_rule()`（`backend/modules/ga4/insights/anomaly_rules.py:93-182`）：對每條規則各自抓一次「觀測值」+ 8 週歷史基線（`_fetch_metric_total`，共 9 次 GA4 API 呼叫／規則／每次評估），`api_metric = SUPPORTED_METRICS[rule.metric_key]`——`conversions` 規則跟當日總覽拆分前一樣，用的是官方 `conversions` 指標，是「該屬性所有關鍵事件」的總和，目前確實全部事件混在一起判斷。
- 排程（`backend/core/scheduler/ga4_jobs.py`）：hourly 規則每小時 :10 跑一次（`run_ga4_insights_intraday_job`），daily 規則每天 09:00 跑一次（`run_ga4_insights_daily_job`），各自呼叫 `repository.list_enabled_rules(db, frequency=...)` 抓出符合頻率的規則，逐條 `evaluate_rule`，**規則之間互相獨立、無共用快取**——同屬性、不同 `metric_key` 的兩條規則會各自重新查一次基線，無 dedup。這點很重要：代表規則本來就是「每條規則自己的 API 成本」，不是像當日總覽那樣一次刷新要把所有東西算完。
- 前端建立規則表單（`frontend/src/components/GA4Insights/AlertsTab.jsx:41-45`）：「轉換／工作階段／營收」三選一下拉，沒有事件層級選項。
- 既有的關鍵事件拆分前例：到達頁的 `keyEvents:{event}` 動態指標語法（`landing_pages.py`）與這次當日總覽的 `conversion_events`/`conversions_by_event`（docs/50）都已驗證這個語法在真實 GA4 資料下可行。

## 跟當日總覽拆分（docs/50）的關鍵差異

docs/50 的最大顧慮是「方案 B 一次刷新要把全部事件的基線都算好」會讓 API 用量隨事件數增加，所以才需要 Top 5 上限。**告警規則的架構天生沒有這個問題**：

- 規則本來就是使用者一條一條「自己選擇要建立」的，不是系統自動幫每個事件都算一份
- 每條規則的評估成本固定是 9 次 API 呼叫，跟今天完全一樣，不會因為「支援按事件拆分」這個功能本身而變重
- 使用者要看「購買」異常，就自己建一條「轉換 · purchase」規則；還想看「加入購物車」，再建第二條——用量隨使用者**自己建立的規則數**線性增加，這在今天（使用者可以建多條 sessions/conversions/purchase_revenue 規則）就已經是既有行為，不是新引入的風險

所以這個功能不需要像 docs/50 那樣設「最多 5 個」的事件數上限；真正該注意的是「事件選單的來源」跟「新增一個查詢維度後的相容性」。

## 技術方向

### 1. 資料庫：`GA4AnomalyRule` 新增 `key_event` 欄位（nullable）

- 新增 `key_event = Column(String(80), nullable=True)`；`NULL` = 全部關鍵事件（現況、預設值，向下相容——既有規則不用動）
- 只有 `metric_key == "conversions"` 時 `key_event` 才有意義；`sessions`／`purchase_revenue` 規則一律當作 `key_event` 必須是 `None`
- Migration 比照 `20260727_ga4_insights_share_token.py` 的 idempotent additive 寫法（`add_column` 前先檢查欄位是否已存在）

### 2. 評估邏輯：`evaluate_rule()` 依 `key_event` 切換動態指標

```python
api_metric = SUPPORTED_METRICS.get(rule.metric_key)
if rule.metric_key == "conversions" and rule.key_event:
    api_metric = f"keyEvents:{rule.key_event}"
```

其餘查詢/基線/異常判斷邏輯完全不變——這正是這個功能能做得這麼輕量的原因：只是換了一個字串，不是換一套機制。

### 3. 建立/編輯規則的驗證

- `RulePayload` 新增 `key_event: str | None = None`
- 驗證比照到達頁既有的 `LANDING_PAGE_KEY_EVENT_PATTERN`（`^[A-Za-z0-9_]{1,40}$`），防止把任意字串接進 GA4 動態指標語法
- 業務規則：`key_event` 非空但 `metric_key != "conversions"` → 拒絕（400），避免使用者誤解「工作階段也能挑事件」

### 4. 事件選單來源：新增輕量端點，不影響排程用量

- 新增 `GET /anomaly-rules/available-key-events?property_id=...`，查詢 `dimensions=["eventName"], metrics=["keyEvents"]`、近 7 天（沿用 `_trailing_period(7)`），回傳這個屬性目前有資料的事件名稱清單
- 這支查詢**只在使用者打開「建立/編輯規則」表單、且選了「轉換」時**呼叫一次，不是排程的一部分，不影響上面提到的「每條規則 9 次呼叫」的固定成本
- 用 7 天窗口而非「當日至今」，避免一大早開表單時事件清單是空的（docs/50 的當日總覽卡片可以接受「當日還沒發生就不列」，但這裡是設定畫面，應該讓使用者看到這個屬性「平常會有」的事件）

### 5. 前端：告警規則表單多一個條件顯示的下拉

- `AlertsTab.jsx` 的 metric_key 選到「轉換」時，旁邊多顯示一個「關鍵事件」下拉（預設「全部關鍵事件」+ 上述端點回傳的事件清單）
- 規則清單／告警歷史顯示文字補上事件名稱，例如「轉換（purchase）· hourly」，`None` 時維持現況顯示「轉換」
- `build_alert_message()` 的通知文字同樣要帶上事件名稱，避免使用者收到 LINE/Email 通知時看不出是哪個事件異常

### 6. 序列化：`serialize_rule`/`serialize_event` 補上 `key_event` 欄位

單純多回傳一個欄位，前端才有東西可以顯示。

## API 用量評估

- 排程固定成本：**不變**。每條規則仍是 1 次觀測 + 8 次基線 = 9 次 GA4 呼叫，`key_event` 只是換了指標字串，不會讓現有規則變貴
- 新增成本只有兩處，且都是「使用者主動觸發」而非排程：
  1. 打開建立/編輯規則表單且選「轉換」時，多 1 次 `available-key-events` 查詢
  2. 使用者自己選擇建立幾條「轉換 · 特定事件」規則，就對應幾組 9 次呼叫——這跟今天使用者可以建多條 sessions/conversions 規則是同一種、本來就存在的線性成長，不是本次新增的風險
- 結論：不需要像 docs/50 那樣設事件數上限

## 待確認問題

1. **`key_event` 為必填的驗證時機**：`metric_key != "conversions"` 卻帶了 `key_event` 要直接 400 拒絕，還是後端自動忽略（存成 `None`）就好？（傾向明確拒絕，避免使用者以為設定生效了）
2. **事件選單的查詢窗口**：暫定近 7 天（跟到達頁 `available_key_events` 的既有精神一致），是否要跟到達頁一樣可調整，還是先固定 7 天就好？
3. **既有規則的呈現**：現有規則預設 `key_event = None`（全部關鍵事件），編輯既有規則時要不要順便提示「這條規則目前是全部關鍵事件加總」，比照當日總覽轉換卡片那顆 ⓘ？
4. **範圍**：這次只做「告警設定」的規則建立/編輯/評估/通知文字，KPI 目標（`GA4KpiTarget`）要不要一併比照拆分？（KPI 目標的 `metric_key` 也有 `conversions`，但性質是「累計進度追蹤」而非「異常告警」，使用情境不同，傾向本次不做，另外評估）

## 不在本次範圍內

- KPI 目標頁籤的關鍵事件拆分（見上方待確認問題 4，視回覆另外規劃）
- 事件選單來源比照當日總覽做「當日次數排序＋上限 N 個」——告警規則場景不需要，見上方分析
- 修改既有規則的預設行為（`key_event = None` 的既有規則行為與數字完全不變）
