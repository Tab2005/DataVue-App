## 一、現況盤點：從商業角度看這個專案有什麼

### 1.1 產品成熟度

| 面向 | 現況 | 商業意涵 |
| :--- | :--- | :--- |
| 程式碼規模 | 568 檔／111,297 行（docs/71） | 已遠超 MVP，是可交付產品 |
| 部署 | Zeabur 三服務（backend／frontend／Andromeda worker），生產架構 Option D 已驗證 | 可立即開帳號給外部使用者 |
| 測試 | 後端 17,962 行測試 + 前端 hooks/pages 測試 | 有基本迭代安全網，敢改 |
| 多租戶 | `teams`／`team_members`／`team_invites` + `visible_ad_account_ids` 白名單 | **代理商多客戶結構已存在** |
| 權限 | `modules`／`user_module_access`／RBAC + ABAC | **模組級開關已存在＝方案分級的現成掛載點** |
| 收費 | 全專案 grep `subscription｜billing｜stripe｜quota｜plan_tier` **零匹配** | 完全沒有金流與用量計量 |

**結論：技術產品已完成度很高，商業產品完成度接近零。** 缺的不是功能，是「怎麼收錢」與「誰來用」。

### 1.2 真正的差異化在哪

市面上跨平台儀表板（Looker Studio、Whatagraph、Swydo、AgencyAnalytics）已經很多，**單純「把 FB＋GA4＋GSC 畫成圖表」沒有定價權**。DataVue 真正稀缺的是三個 AI／統計模組：

| 模組 | 規模 | 稀缺性評估 |
| :--- | :--- | :--- |
| **Meta Andromeda**（AI 素材評分） | 12,127 行／52 檔，全專案最大模組 | ★★★★★ 有觀測匯入 → 特徵 → 評分管線 → Review Queue → 專家標註 → 自適應校準的**完整學習閉環**（docs/17、30、32）。這不是套 LLM API，是有回饋迭代的模型系統，競品極少 |
| **MMM 貢獻衡量** | 3,388 行，含 `engine.py` 邊際貢獻運算 | ★★★★☆ 中小代理商幾乎買不到、也做不出來的東西 |
| **GA4 即時轉換洞察** | 4,745 行，含異常規則 + LINE 推播 + 凍結快照分享 | ★★★☆☆ 分類規則（landing_pages／items／channels）+ 異常偵測有價值 |
| GSC 內容缺口 AI 建議 | docs/37 Phase 1-2 已完成 | ★★★☆☆ SEO 內容題目生成，是加值不是主打 |

> **定位建議**：不要賣「儀表板」，要賣「**Meta 廣告素材的 AI 診斷與投放決策**」，把 GA4／GSC／MMM 當作使其可信的證據層。前者有定價權且難複製，後者是入場券。

### 1.3 現行 Landing Page 與產品定位不符（需修正）

`frontend/src/pages/Landing.jsx`（141 行）目前把四個模組平等並列，主打「跨平台數據收斂」——這是**紅海定位**，且完全沒有提到 Meta Andromeda。同時 CTA 已寫「免費試用」，但系統中沒有任何 trial 邏輯。這是目前最直接的行銷落差。

## 二、四個商業化阻斷點（依觸發時機分級）

以下項目在程式碼中已確認。**注意：經 2026-08-13 查證，這些阻斷點的觸發時機不同——只有 D 與 C 的一部分會阻擋「開始收費」，A 與 B 阻擋的是「自助註冊規模化」。**

### 阻斷點 A：Facebook 串接的上線摩擦（2026-08-13 重新定性）

- **現況證據**：`database/models/team.py` 有 `fb_app_id`、`fb_access_token`；`frontend/src/components/Settings/FacebookSettingsTab.jsx` 要求使用者填入 `app_id`／`app_secret`；`core/config.py` **沒有任何平台級 FB app 設定**（grep `FB_APP_ID｜FACEBOOK_APP｜SYSTEM_USER` 零匹配）。即目前是完全的 per-user／per-team BYOK。

- **關鍵釐清（本次修訂重點）**：Meta 的 **Standard Access** 只能操作「自己擁有或管理」的資產；必須存取**他人**廣告帳戶才需要 Advanced Access，才觸發 App Review + Business Verification。現行 BYOK 架構等於「客戶自建 app、自任 admin、只讀自己的廣告帳戶」，**因此你與客戶雙方都不需要 App Review，也不需要 Business Verification，更不需要統一編號。**

- **初版判斷的錯誤**：初版將「第一天送 Meta App Review」列為最高優先，屬時序誤判。正確理解是：**App Review 是自助註冊規模化的門檻，不是開始收費的門檻。** 種子期完全可以靠現有 BYOK 架構合法收費營運。

- **真正的問題（仍然存在）**：
  1. **UX 摩擦**——要求行銷人員自行到 Meta 開發者後台建立 app 並取得 token，一般客戶做不到。種子期由你代為完成（high-touch）可吸收，但**這條路撐不過 10 家客戶左右**。
  2. **API 速率層級**——Meta 於 2026-05-04 將 AMSA 改名為 Marketing API Access Tier 並分為兩級，客戶自建的新 app 起始額度較低。客戶若有多個廣告帳戶可能觸頂。**此項影響程度未經實測，應於第一家種子客戶上線時驗證。**

- **分階段解法**：

  | 階段 | 做法 | 需要統編／送審？ |
  | :--- | :--- | :--- |
  | 種子期（5–10 家） | 續用 BYOK，由你代客戶建 app 與串接 | 皆不需要 |
  | 規模化自助註冊 | 平台級 Meta App + Business Verification + App Review（`ads_read`） | 需統編、需送審 |

### 阻斷點 B：Google OAuth 尚未通過驗證

- **現況證據**：`core/config.py` 使用平台級 `GOOGLE_CLIENT_ID`／`GOOGLE_CLIENT_SECRET`（架構正確），但 GA4／GSC 屬 Google **sensitive scope**。
- **問題**：未通過 OAuth verification 前，非測試名單使用者會看到「此應用程式未經驗證」警告，且測試使用者有人數上限。
- **觸發時機**：與阻斷點 A 同性質——種子期客戶數在測試名單上限內，可先加入測試使用者名單運作；**未驗證警告會影響專業觀感，但不阻擋收費**。真正卡住的是自助註冊規模化。
- **解法**：送 Google OAuth verification（需隱私權政策頁、應用程式首頁、用途說明影片）。與阻斷點 A 的規模化階段併行處理。

### 阻斷點 C：沒有計費、用量計量與方案分級

- **現況證據**：全專案零 billing 相關程式碼；`is_super_admin` 由「第一個註冊的使用者」自動取得（`modules/auth/dependencies.py:115`），註冊完全開放無 gating。
- **好消息**：`UserModuleAccess` + `Module.enabled` + `PermissionService.check_module_access()` **已經是完整的模組開關**。方案分級不需要新架構，只需在既有權限層上加一層「方案 → 模組集合」的對應，再加訂閱狀態欄位。這是本專案商業化成本最低的一環。
- **BYOK 的雙面性**：AI key 由使用者自帶（`user.zeabur_api_key`／`gemini_api_key`／`openrouter_api_key`），代表**平台幾乎沒有 AI 變動成本，毛利極高**；但也代表客戶得自己去辦 AI 帳號，是另一道上線摩擦。建議中高階方案改為「平台代付 AI 額度」，把 BYOK 降級為進階選項——這同時是漲價理由。

#### 補充：統一編號的真正定位（2026-08-13 新增）

統編常被誤認為「Meta 送審的成本」。實際上在阻斷點 A 重新定性後，**Meta 那條路種子期根本不需要統編**；但統編仍然是必需品，理由與 Meta 無關：

- 目標客群是代理商，屬 **B2B**。台灣 B2B 客戶付月費需要**統一發票**才能列為營業費用報帳。**沒有發票，採購會在對方會計端直接卡住**——這是收費本身的前提，不是平台串接的前提。
- **統編 ≠ 必須開公司**：獨資商號（行號）走**商業登記**即可取得統編，成本與流程遠低於設立有限公司，不需為了 Meta 而設立公司。
- **不建議**借用他人公司統編或掛靠：Meta 的 Business Verification 要求文件與實際營運主體一致，且帳務與法律風險不對稱。

> **待查證**：商業登記的實際規費、作業天數，以及 Meta 對台灣主體 Business Verification 的文件清單，本文件無可靠即時資訊，請向記帳士或經濟部商業司確認，勿引用本文件推估。

### 阻斷點 D：Facebook Token 60 天到期，且無任何提醒或續期機制（**最高優先**）

- **現況證據**：`modules/auth/service.py:235` 的 `exchange_for_long_lived_token` 取得的是 Meta 的 **60 天長效 token**；`token_expires_at` 有落地，`/token-status` 端點也已回傳 `days_remaining`。但 `core/scheduler/` 底下只有 `contribution_jobs`／`ga4_jobs`／`meta_andromeda_jobs`／`report_jobs` 四個 job 檔，`grep -niE "expir" core/scheduler/*.py` **零匹配**——沒有任何到期提醒或自動續期排程。
- **問題**：客戶每 60 天會**無聲斷線**，且 BYOK 模式把重新授權的責任推給客戶自己。這在有付費客戶後是直接的服務事故。
- **解法**：在既有 `core/scheduler/` 架構新增到期前提醒 job，推播管道可直接複用現成的 `modules/line`。前端已有 `days_remaining` 可用，實作成本低。
- **優先度**：**A／B 阻擋的是規模化、C 可與收費並行處理，只有 D 會直接傷害已付費客戶。這是本文件中唯一「有付費客戶前就必須完成」的技術項目。**

## 三、商業模式建議

### 3.1 主模式：垂直 SaaS，鎖定「中小型數位行銷代理商」

**為什麼是代理商而不是品牌主：**

1. 產品裡的多租戶結構（team + 廣告帳戶白名單 + 邀請碼）本來就是為代理商服務多客戶而設計的；
2. 代理商有**週期性交付報告的剛性需求**——週報引擎與凍結快照分享正好命中；
3. 單一代理商帶進 10–30 個廣告帳戶，**ARPU 是品牌主的數倍**，且獲客成本攤薄；
4. 代理商彼此高度連結，口碑擴散快。

**次要客群**：自建投放團隊的中大型電商（有 Meta 素材迭代需求、月廣告預算達一定規模者）。

### 3.2 定價架構建議（新台幣，月付；年付 8 折）

分級軸線刻意選用**「廣告帳戶數 × 模組」**而非使用者席次——因為成本與價值都跟著廣告帳戶走，且 `visible_ad_account_ids` 已存在，計量容易。

| 方案 | 月費 | 廣告帳戶 | 模組 | 目標客群 |
| :--- | ---: | :---: | :--- | :--- |
| **Trial** | 免費 14 天 | 1 | 全功能（含 Andromeda） | 轉換用，刻意開放 Andromeda 建立依賴 |
| **Starter** | NT$1,500 | 1 | GA4 洞察 + GSC + 週報 | 單一品牌主、接案 freelancer |
| **Growth** | NT$4,800 | 5 | Starter + **Meta Andromeda** + FB Ads | 小型代理商、自營電商（**主力方案**） |
| **Agency** | NT$12,800 | 20 | Growth + **MMM 貢獻衡量** + 多團隊 + 白標分享頁 | 中型代理商 |
| **Enterprise** | 報價 | 不限 | 全功能 + 私有部署 + SLA + 客製規則 | 大型代理商／集團品牌 |

**定價邏輯說明：**
- Andromeda 放在 Growth 而非最高階——它是**最強的付費理由**，藏太高會讓主力方案賣不動。
- MMM 放 Agency，因為它的解讀需要專業能力（見 docs/26 判讀指南），適合服務型客戶，也是自然的升級鉤子。
- Starter 刻意不含 FB Ads，避免在阻斷點 A 解決前湧入大量串接失敗的低價客戶。
- 上述金額為依台灣中小代理商付費水準推估的**起始提案，非市場驗證結果**，應在種子客戶訪談後校正。

### 3.3 第二收入來源（不需新產品）

1. **上線導入服務（一次性）**：代客戶完成 Meta／Google 串接、指標設定、MMM 分組校準。在阻斷點 A 解決前，這**本來就是必要工作，直接把它變成收入**而非成本。
2. **AI 額度加購**：平台代付模式下的超量計費（BYOK 客戶免此項）。
3. **白標／OEM**：代理商用自己的品牌把分享頁交付給終端客戶。現有 `SharedReport.jsx`／`SharedGA4Insight.jsx`／`SharedAnalyticsInsight.jsx` 已是獨立分享頁，白標化成本低，但 **docs/69 指出分享連結缺 `expires_at` 與存取紀錄，白標商用前必須補**。

### 3.4 刻意「不做」的模式

- **不做純買斷／一次性授權**：AI 模型需要持續校準（Andromeda 學習閉環），買斷會讓價值與收入脫鉤。
- **不做免費 freemium 長期版**：BYOK 雖使 AI 成本近零，但 Zeabur 三服務 + Postgres + 素材 volume 有固定成本，且免費用戶會佔用 Meta API 配額。用 14 天全功能試用取代。
- **短期不做自助信用卡付款**：前 20 家客戶用人工開票 + 匯款即可。金流串接的工程成本，應該等到有人願意付錢之後再花。

## 四、推廣策略與執行順序

### 階段一（第 0–2 月）：以人工服務驗證付費意願（不送審）

此階段**不做任何規模化行銷**。目標是驗證付費意願與取得案例。

> **2026-08-13 修訂**：本階段**不送 Meta App Review、不辦 Business Verification**。依阻斷點 A 的重新定性，BYOK 架構在種子期已可合法運作，送審屬階段三規模化前的工作。此修訂讓階段一的行政負擔大幅下降。

| 動作 | 說明 | 為何在此階段 |
| :--- | :--- | :--- |
| **補 FB Token 到期提醒排程（阻斷點 D）** | 掛在既有 `core/scheduler/`，推播複用 `modules/line` | **唯一必須趕在收費客戶之前完成的技術項目**，否則客戶每 60 天無聲斷線 |
| 手動招募 5–10 家種子客戶 | 從既有人脈／社群直接接觸，**由你親自完成 Meta app 建立與串接**（吸收阻斷點 A 的 UX 摩擦） | 驗證付費意願，取得真實數據 |
| 辦理商業登記取得統編 | 目的是**開發票**，非為 Meta 送審（見 §二阻斷點 C 補充） | B2B 收月費的前提；若種子期只收導入費可稍晚，但收月費前必須完成 |
| 客戶問題訪談（3 位代理商窗口） | 驗證「素材診斷」是否真的比「跨平台報表」更痛 | **答案會決定 §1.2 定位是否要整份調整**，成本最低、資訊價值最高 |
| 種子期收費：導入費 + 月費折扣鎖一年 | 折扣換取「可具名的成功案例 + 使用回饋」 | 有付費才是真需求 |
| 補 docs/69 列出的商用必要缺口 | 分享連結 `expires_at` 與存取紀錄；MMM `auto_group` 真實帳戶驗證（docs/27 明列待上線後補做） | 這兩項在對外交付時會直接被客戶發現 |
| 實測 Marketing API 速率層級影響 | 第一家種子客戶上線時觀察其自建 app 的額度是否觸頂 | 影響 BYOK 路線能撐到第幾家客戶 |
| 補隱私權政策、服務條款、資料刪除說明頁 | 對代理商採購是必要文件，也是日後送審的依賴項 | 可平行進行，但不再是審核的擋路石 |

> **副作用（正面）**：種子客戶提供的真實廣告帳戶，正好補上 docs/69 反覆提到的「本機無真實帳號可測」缺口（GSC docs/37 端到端驗證、MMM auto_group 驗證）。**商業化與技術驗證在此階段是同一件事。**

### 階段二（第 2–4 月）：產品商業化改造

| 動作 | 依附的既有架構 |
| :--- | :--- |
| 方案分級落地：`plan` 欄位 + 「方案 → 模組集合」對應 | **直接複用 `UserModuleAccess`／`Module.enabled`／`check_module_access()`**，不需新權限系統 |
| Trial 生命週期（14 天倒數、到期降級、續約提醒） | 需新增，可掛在 `core/scheduler/` 既有 cron 架構 |
| 用量計量（廣告帳戶數、AI 呼叫次數、報表產出數） | 廣告帳戶數可由 `visible_ad_account_ids` 直接計算 |
| 平台代付 AI 額度模式 | `modules/ai_hub` 已有 provider 抽象與 key fallback 邏輯，加入平台 key 分支即可 |
| 註冊 gating（目前完全開放、首位註冊者自動成為 super admin） | `modules/auth/dependencies.py` — **對外開放前必須處理，這是安全問題不只是商業問題** |
| Landing Page 重新定位 | 見 §1.3。主打 Andromeda，加入方案價目表、真實案例數據、CTA 改為「預約 Demo」 |
| **啟動平台級 Meta App + Business Verification + App Review**（2026-08-13 新增） | 需先有統編。**排在此階段而非階段一**：審核有數週前置時間，必須趕在階段三規模化自助註冊之前完成，但不該拖累階段一的種子客戶驗證 |
| 送 Google OAuth verification | 同上，與 Meta 送審併行，解除「應用程式未經驗證」警告 |

### 階段三（第 4 月起）：規模化獲客

**主要管道（依預期投報率排序）：**

1. **內容行銷 —— 這是本專案最強的管道**
   產品本身持續產出「Meta 素材評分準確率分析」「MMM 貢獻歸因判讀」這類**極稀缺的技術內容**（docs/26、docs/30 幾乎可直接改寫成公開文章）。台灣市場少有人寫到這個深度。
   形式：技術部落格 + LinkedIn 長文 + 行銷社群（各大 FB 廣告投手社團）分享實測數據。
   **關鍵：文章要放真實的、去識別化的評分準確率數字**，這才是可信度來源，也是競品無法模仿的部分。

2. **產品自帶擴散（PLG）—— 已經內建，只差補完**
   凍結快照分享頁與週報分享連結，會被代理商直接發給**終端客戶**。每一個分享連結都是一次品牌曝光。
   需要做的：分享頁加上「Powered by DataVue」與 CTA（白標客戶除外）、補 `expires_at` 與存取紀錄（同時是安全需求與轉換追蹤來源）。
   **這是成本最低、目前完全未被利用的管道。**

3. **代理商社群與夥伴關係**
   直接切入台灣／香港的行銷代理商圈：舉辦小型線上實作 workshop（用 Andromeda 拆解真實素材成效），比投廣告有效得多。
   推薦制：代理商推薦成功，雙方各得 1–2 個月折抵。

4. **LINE 生態的在地優勢**
   `modules/line` 的告警推播是**針對台灣市場的明確差異點**——歐美競品沒有。應該把「異常自動 LINE 通知」放到 Landing Page 主要賣點，而不是埋在功能清單裡。

**建議暫緩的管道**：付費廣告（Google／Meta Ads）。在轉換漏斗（Landing → Trial → 串接成功 → 付費）尚未打通、且阻斷點 A 未解決前投放，等於把預算灌進破桶子。

### 階段四（第 8 月起，選配）：Andromeda 獨立產品化

若 Andromeda 的評分準確率經真實數據驗證站得住腳，可將其拆為獨立訂閱產品或 API 服務，賣給**已有自己儀表板**、只缺素材診斷能力的客戶。這會大幅擴大 TAM。
**前提**：需先累積足夠的跨帳戶標註資料讓模型泛化——這正是階段一種子客戶的長期戰略價值。

## 五、風險與對應

| 風險 | 影響 | 對應 |
| :--- | :--- | :--- |
| **FB Token 60 天到期無提醒（阻斷點 D）** | 付費客戶無聲斷線，是直接的服務事故 | **收費前必須補到期提醒排程**；本文件中優先度最高的技術項目 |
| Meta App Review 未過或延宕 | 阻擋**自助註冊規模化**（非種子期收費） | 種子期以 BYOK 繞開，不受影響；規模化前預留審核時間，並確保 GA4／GSC／MMM 在無 FB 時仍能獨立交付價值（現況架構支援） |
| BYOK 路線的 UX 摩擦無法規模化 | 約 10 家客戶後人工上線成本失控 | 以此為觸發點啟動統編 → BV → App Review；不要等到痛了才開始，審核有前置時間 |
| Marketing API 速率層級觸頂 | 客戶自建 app 額度不足，多帳戶客戶功能受限 | 第一家種子客戶上線時實測（見 §四階段一）；影響程度目前未知 |
| Andromeda 準確率在他人帳戶不如預期 | 核心定價權崩塌 | 種子期先用「輔助診斷」而非「保證成效」定位；docs/30 的準確率分析要對客戶誠實揭露 |
| 平台 API 政策變更（Meta／GA4 配額、欄位棄用） | 功能中斷 | 已有 `metrics_registry` 抽象層可緩衝；需建立 API 變更監控 |
| 單人維運，客戶增長後支援量爆炸 | 交付品質下滑 | 定價刻意偏高、客戶數刻意偏少；優先服務 Agency 級客戶而非衝量 |
| BYOK 客戶的 AI key 外洩疑慮 | 採購阻力 | 已有 Fernet 加密存儲，**應主動寫成安全說明文件**作為銷售素材，而非被動等客戶問 |
| 開放註冊 + 首位使用者自動 super admin | 資安事故 | 對外開放前必須修（階段二） |

## 六、建議的下一步（最小可行順序）

> **2026-08-13 修訂**：初版第 1 項為「啟動 Meta App Review」，依阻斷點 A 重新定性已移除，改置於規模化階段。

1. **本週**：確認目標客群假設——先找 3 位認識的代理商窗口做問題訪談，驗證「素材診斷」是否真的比「跨平台報表」更痛。**這一步的答案會決定整份定位是否要調整**，且成本最低，因此排第一。
2. **本週**：補 FB Token 到期提醒排程（阻斷點 D）。這是唯一「有付費客戶前必須完成」的技術項目。
3. **兩週內**：改寫 Landing Page 定位（§1.3），加入方案價目與 Demo 預約。
4. **一個月內**：完成 3–5 家種子客戶的人工上線，開始收導入費；同時實測 Marketing API 速率層級。
5. **收月費前**：辦理商業登記取得統編（為了開發票，非為 Meta）。
6. **之後**：依 §四階段二清單進行商業化改造；BYOK 上線成本開始失控時（約 10 家客戶）啟動 BV + App Review。

> **貫穿全文的核心判斷**：這個專案的技術風險已經很低，剩下的全是市場風險。因此接下來的資源，應該從「再寫功能」轉向「找客戶、驗證定位」。
>
> 經 2026-08-13 修訂後，這個判斷更強了——原本以為的最大行政障礙（Meta App Review 與統編）在種子期並不存在，**現在真正擋在收費前面的只有兩件事：一個到期提醒排程，以及有沒有人願意付錢。** docs/69 列出的技術缺口中，只有「分享連結到期與存取紀錄」及「MMM 真實帳戶驗證」兩項與商業化直接相關，其餘可以先放著。
