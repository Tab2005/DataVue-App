# 49_GA4 當日總覽轉換事件拆分下拉選單擴充構想

## 背景

延續 [[48_GA4_當日總覽轉換指標口徑標示]]：目前「當日總覽」的「轉換」卡片是 GA4 `conversions` 指標的總和，把該屬性所有被標記為關鍵事件的事件（可能包含加入購物車、註冊等）混在一起算，已先加 ⓘ 提示標示口徑。使用者詢問能否進一步在同一張卡片加下拉選單，選特定關鍵事件（例如只看「購買」）——GA4 預設關鍵事件是 `purchase`，但屬性之後可能會新增其他關鍵事件，下拉選單要能自動反映 GA4 實際設定，而不是寫死選項。

## 現況（相關程式碼）

- `backend/modules/ga4/insights/dashboard.py::_fetch_intraday_dashboard_payload`：主查詢 `metrics=DASHBOARD_METRICS`（`sessions`/`conversions`/`purchaseRevenue`），`dimensions=["hour", "sessionDefaultChannelGroup"]`，只抓「今天」
- 基線（平常區間）計算：對每個指標各自呼叫 `_fetch_metric_total` 抓過去 8 週同一星期幾的歷史資料（`_historical_dates`），共 `3 指標 × 8 週 = 24` 次額外 GA4 API 呼叫，已經是整個功能裡最重的部分
- 快取：整份 payload 存成一筆快照（`kind="intraday_dashboard"`，`(property_id, date)` 唯一），前端「立即刷新」有 10 分鐘冷卻
- 既有的關鍵事件拆分前例：`landing_pages.py` 用 `keyEvents:{event}` 動態指標語法查特定事件，`available_key_events` 靠 `dimensions=["landingPage", "eventName"]` 撈出這個屬性實際有的事件名稱，前端下拉選單直接用這份清單——**這正是「自動抓 API 資料而增加」的既有做法，不用另外設計**

## 技術方向

### 1. 用 `keyEvents`/`keyEvents:{event}` 取代 `conversions`，比照到達頁做法

`conversions` 是總和型指標，沒有「選特定事件」的語法；GA4 的 `keyEvents:{event_name}` 動態指標才能查單一事件。要拆分下拉選單，「轉換」這張卡片的底層指標要從 `conversions` 換成 `keyEvents`（全部關鍵事件，等同現況）或 `keyEvents:{event}`（單一事件）。

### 2. 下拉選單清單怎麼自動增加

主查詢額外加 `eventName` 維度（`dimensions=["hour", "sessionDefaultChannelGroup", "eventName"]`，或另開一支 `dimensions=["eventName"]` 的輕量查詢），從回傳的 `eventName` 去重就是這個屬性目前實際存在的關鍵事件清單。之後 GA4 後台新增關鍵事件，隔天資料一來，這份清單自然會多出新選項，前端不用改程式碼、也不用維護白名單。

### 3. 核心取捨：基線異常判定要不要拆到每個事件

這是本次最大的設計決策，直接影響 API 用量與使用者體驗：

- **方案 A：即時查**——下拉選單切換到某個事件時，前端才打一次新的請求，後端當場對那個事件做 8 週基線查詢。
  - 優點：平常（不特別去選事件時）完全不增加 API 用量，只有真的要看某個事件的異常判定時才付出成本
  - 缺點：切換下拉選單要等（8 次歷史查詢有延遲），且「刷新」跟「選事件」變成兩種不同的資料新鮮度，使用者體感可能覺得奇怪
- **方案 B：一次算好**——每天固定刷新（或手動「立即刷新」）時，把當天資料裡實際出現過的關鍵事件全部一起算基線，存進同一份 payload（例如 `payload.conversions_by_event = { "purchase": {...}, "add_to_cart": {...} }`），下拉選單切換純粹是前端本地換一個 key 顯示，不用重打 API。
  - 優點：切換下拉選單瞬間反應，使用者體驗好；資料新鮮度跟其他卡片一致（都是同一次刷新的結果）
  - 缺點：API 用量隨這個屬性關鍵事件的數量線性增加——假設有 3 個關鍵事件（含「全部」共 4 種口徑），基線查詢會從現在的 24 次變成 `(2 個其他指標 × 8) + (4 種轉換口徑 × 8) = 48` 次，接近翻倍；如果關鍵事件多達 10 個以上，會變得很重（但多數電商屬性關鍵事件通常落在 2-5 個之間，一般情況可接受）

**傾向方案 B**：「立即刷新」本來就有 10 分鐘冷卻限制用量，且下拉切換不用等待對使用者體感比較重要；額外好處是這份「拆分後的每個事件」資料之後也能餵給 AI 白話解讀（例如分開講「加購成長但購買持平」）。但正式拍板前建議先確認這個屬性實際的關鍵事件數量不會太多，避免基線查詢暴增。

### 4. 快照不需要因為選了哪個事件而分開存

跟到達頁/商品的渠道篩選（`ch_`/`chg_` 雜湊後綴）不同——那邊是因為「篩選條件」會改變主查詢結果的列數與內容，所以要分開存快照。這裡如果採方案 B，同一份 payload 本來就內含全部關鍵事件的細節，下拉選單只是前端決定要顯示 payload 裡的哪一段，**不需要改變快照的 `kind` 或存成多筆**，維持現況「一天一筆」即可。

## 待確認問題（動工前需拍板）

1. 「全部關鍵事件」預設要不要維持現況（跟現在一樣是總和），下拉選單只是多一個「只看某事件」的細看選項，還是要換成預設就是「購買」（使用者提到「GA4 預設是購買」，但這是指 GA4 系統本身內建的第一個關鍵事件，不代表這個屬性只有這一個，需要用第 2 點的自動偵測清單來確認實際狀況）
2. 這張卡片的「異常」判定邏輯（跟平常區間比較）在方案 B 下要對每個事件各自判定，還是只對「全部關鍵事件」判定、單一事件只顯示數字不判異常（降低基線查詢量的折衷做法）
3. 事件數量是否要設保護上限（例如只列前 N 個依當日次數排序，避免罕見/測試用事件把下拉選單塞滿）
4. 這個拆分功能是否也要同步加到「渠道對照」分頁的 `daily_channel`（該分頁也有轉換相關指標），或先只做「當日總覽」這張卡片
