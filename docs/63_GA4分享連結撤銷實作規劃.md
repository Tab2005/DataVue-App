# 63_GA4 分享連結撤銷實作規劃

實作日期：2026-07-31
對應項目：docs/59「建議處理順序」第 4 項 —— **P1-3 分享連結無法撤銷、無期限、無存取紀錄**
狀態：**已完成**（撤銷；`expires_at` 與存取紀錄依 docs/59 原文「可視需求排期」，不在本次範圍）

---

## 1. 問題重述

> `share_token` 一旦產生就永久有效⋯⋯對一個「把 GA4 數據公開給未登入者」的功能來說，這三項缺一都算是治理缺口。**誤發給錯的人之後沒有任何補救手段。**

docs/59 的建議是「至少補 `DELETE /snapshots/{id}/share`（把 token 設回 NULL）」。docs/61 已經把分享連結搬到獨立的 `ga4_shared_snapshots` 表，所以實作方式跟原建議略有不同（不再有 token 欄位可設 NULL），但端點形狀維持一致。

---

## 2. 三個設計決策

### 2.1 以「來源快照」為單位整組撤銷，不是單條 token

docs/61 之後，同一個分頁每次資料變動後再分享都會產生**一條新的連結**（凍結副本）。而 UI 沒有「我發過哪些連結」的清單，使用者只看得到最後產生的那一條。

若撤銷只作用在單一 token，使用者根本沒辦法收回早上發出去的那條——那正是最需要撤銷的情境。所以 `DELETE /snapshots/{snapshot_id}/share` 撤銷該快照分享出去的**全部**連結，回傳 `revoked_count`。

前端按鈕文案與 tooltip 都明講「不只畫面上這一條」，避免使用者誤以為只收回眼前那條。

### 2.2 軟刪除（`revoked_at`）而非 DELETE

這是安全治理功能，「**什麼內容曾經被公開出去、何時收回**」本身就是該留下的紀錄；`payload` 一併保留，事後才查得出當初到底發了什麼。硬刪除會把這些一起清掉。

代價是查詢端必須過濾 `revoked_at IS NULL`，漏掉就等於撤銷無效——所以過濾集中在 repository 的兩支查詢，並各有測試把關（見第 4 節突變測試）。

### 2.3 可重複執行，且不用狀態碼洩漏「有沒有分享過」

沒有有效連結時回 `200` + `revoked_count: 0`，不是 404：

- 使用者連按兩次撤銷不該看到錯誤
- 「這個快照有沒有被分享過」不該從狀態碼推得出來

（快照本身不存在或不屬於呼叫者時仍是 404，沿用 docs/60 的授權慣例。）

## 3. 實作內容

| 層 | 變更 |
|---|---|
| Model | `GA4SharedSnapshot.revoked_at`（DateTime, nullable） |
| Migration | `20260731_ga4_shared_snapshot_revoked_at`：純新增 nullable 欄位，既有資料不受影響 |
| Repository | `revoke_shared_snapshots_for_source()`；`get_shared_snapshot_by_token()` 與 `get_latest_shared_snapshot_for_source()` 都加上 `revoked_at IS NULL` 過濾 |
| Service | `sharing.revoke_share_links(db, *, snapshot_id) -> int` |
| Router | `DELETE /snapshots/{snapshot_id}/share`，權限與「產生分享連結」相同（`require_ga4_insights_view`）＋ docs/60 的屬性檢查 |
| 前端 | `ga4InsightsService.revokeShareLinks()`；`AIInsightNote` 加「撤銷分享連結」按鈕（含 `window.confirm` 二次確認與撤銷結果提示） |

### 為什麼 `get_latest_shared_snapshot_for_source` 也要過濾

這支是 docs/61「內容沒變就沿用同一個 token」的判斷來源。若不排除已撤銷的副本，**撤銷後再按分享會沿用到那條已收回的 token**——原本失效的連結突然又能打開，撤銷等於被悄悄還原。這是本次最容易漏掉的一點，有專門測試。

### 權限為什麼用 view 而不是 manage_alerts

能把連結發出去的人就該能收回來。若撤銷需要更高權限，誤發之後反而沒有補救手段，與本項目的目的相反。

### 前端按鈕位置

刻意放在「產生分享連結」旁邊，而**不是**放在連結顯示區塊裡。真正需要撤銷的情境是「昨天誤發、今天回來收回」，那時畫面上根本沒有連結可看（`shareToken` 只存在於當次 session 的 state），藏在連結區塊裡就等於用不到。

## 4. 測試

新增 `backend/tests/test_ga4_share_link_revoke.py`（8 個）：

1. 撤銷後公開端點回 404
2. 軟刪除：列與 payload 保留、`revoked_at` 有值
3. 整組撤銷：同一快照的兩條連結都失效、`revoked_count == 2`
4. **撤銷後再分享會發全新 token**（撤銷不可被悄悄還原）
5. 可重複執行：從未分享過 → `revoked_count: 0` 且非 404；撤銷兩次第二次為 0
6. 不誤傷其他快照的連結
7. 別人屬性的快照 → 404，且該連結不受影響
8. 快照不存在 → 404

## 5. 不在本次範圍

docs/59 P1-3 列的另外兩項，原文即為「可視需求排期」：

- **`expires_at`（連結自動過期）**：需要決定預設期限與 UI 呈現，且會影響已發出的連結，宜獨立評估
- **存取紀錄（連結被誰看過幾次）**：`GET /share/{token}` 是公開端點，記錄訪客資訊牽涉隱私與法遵，需要先定案要記什麼

有了 `revoked_at` 之後這兩項都更好做：過期本質上是「到期自動視為撤銷」，可沿用同一條查詢過濾。
