# 52_GA4 告警規則關鍵事件拆分實作規劃

## 背景

延續 [[51_GA4_告警規則關鍵事件拆分擴充構想]] 拍板的 4 個決策，本文件把設計拆成可依序執行的實作步驟。

## 拍板決策（承接 51 號）

1. `key_event` 非空但 `metric_key != "conversions"` → 全部拒絕（422，pydantic cross-field 驗證）
2. 事件選單查詢窗口固定近 7 天，不開放調整；跟規則的 `check_frequency`（hourly/daily）無關，純粹是「查一次這個屬性有哪些關鍵事件」的資料來源
3. `key_event = None`（全部關鍵事件）的規則，UI 要加提示說明是全部關鍵事件加總
4. KPI 目標頁籤本次不做

## 實作步驟（依序執行）

### 步驟 1：資料庫 — `GA4AnomalyRule` 新增 `key_event` 欄位 ✅ 已完成

- 檔案：`backend/database/models/ga4_insights.py`，`GA4AnomalyRule` 新增 `key_event = Column(String(80), nullable=True)`（緊接 `metric_key` 之後）；`NULL` = 全部關鍵事件（現況、預設值）
- 新增 alembic migration（比照 `20260727_ga4_insights_share_token.py` 的 idempotent 寫法：`upgrade()` 前先 `inspector.get_columns()` 檢查欄位是否已存在才 `add_column`，`downgrade()` 對稱檢查後 `drop_column`），不需要 index（不會拿來查詢過濾，只是讀取顯示與組指標字串用）
- **向下相容**：既有規則該欄位一律是 `NULL`，`evaluate_rule` 判斷邏輯以「有沒有值」為準，不影響任何既有規則的評估結果

### 步驟 2：後端邏輯與驗證 ✅ 已完成

- 檔案：`backend/modules/ga4/insights/anomaly_rules.py::evaluate_rule`
  - 在算 `api_metric` 之後，加一段：`metric_key == "conversions"` 且 `rule.key_event` 有值時，`api_metric = f"keyEvents:{rule.key_event}"`；其餘查詢/基線/異常判斷邏輯完全不動
  - `build_alert_message()` 補一個可選的 `key_event` 參數，有值時通知文字的指標標籤顯示成「轉換（{key_event}）」，`None` 時維持現況「轉換」——避免使用者收到通知看不出是哪個事件異常
- 檔案：`backend/modules/ga4/insights_router.py`
  - `RulePayload` 新增 `key_event: str | None = None`，加 `@field_validator("key_event")`（比照既有 `KpiTargetPayload._validate_period_key` 的 cross-field 驗證寫法，用 `info.data.get("metric_key")` 拿到已驗證過的 `metric_key`）：
    - 非 `None` 時必須符合既有的 `LANDING_PAGE_KEY_EVENT_PATTERN`（`^[A-Za-z0-9_]{1,40}$`，`_shared.py` 既有常數，語意通用不局限到達頁，直接重用不新增常數）
    - 非 `None` 但 `metric_key != "conversions"` → `raise ValueError`（pydantic 自動轉成 422，同 `period_key` 既有前例，不用額外的 try/except／400 映射）
  - `create_anomaly_rule`/`update_anomaly_rule` 不用改：`payload.model_dump()` 會自動帶上 `key_event`，`repository.create_rule`/`update_rule` 都是 `**payload`／`setattr` 通用寫法，新欄位自動生效
  - `serialize_rule`/`serialize_event` 補上 `"key_event": row.key_event`（`serialize_event` 走 `row.rule.key_event if row.rule else None`，比照現有 `metric_key` 的取法）
  - 新增端點 `GET /anomaly-rules/available-key-events`：
    - Query 參數：`property_id`
    - Service 層新函式 `list_available_key_events(db, *, user, property_id)`（放 `anomaly_rules.py`）：`GA4Service.get_analytics(dimensions=["eventName"], metrics=["keyEvents"], start_date/end_date=_trailing_period(7))`，回傳去重、排序後的事件名稱清單（排除空字串）
    - 查詢失敗時 `raise RuntimeError`，router 比照 `items`/`item-landing-cross` 既有慣例 `except (RuntimeError, ValueError)` → 400；前端這支呼叫失敗時**不擋整個表單**，下拉只是少了「全部關鍵事件」以外的選項（見步驟 3）

### 步驟 3：前端 — 告警規則表單與列表 ✅ 已完成

- 檔案：`frontend/src/components/GA4Insights/AlertsTab.jsx`
  - `metric_key` 選到 `conversions` 時，旁邊多顯示一個「關鍵事件」下拉：預設選項「全部關鍵事件」（對應 `key_event: null`），其餘選項來自 `GET .../available-key-events` 的回傳（掛載/切換到 `conversions` 時才呼叫；呼叫失敗時只顯示「全部關鍵事件」，不阻擋表單其他操作）
  - `metric_key` 切離 `conversions` 時，`key_event` 重設回 `null`（避免殘留舊值造成步驟 2 的 422）
  - 規則清單（`rules.map(...)`）與告警歷史（`events.map(...)`）顯示文字：`key_event` 有值顯示「轉換（{key_event}）」，`None` 時顯示「轉換」＋比照當日總覽卡片同一段提示文字的 ⓘ（「此為 GA4 關鍵事件總和...」），滑鼠移過去顯示同一句說明，維持全站用語一致
- 檔案：`frontend/src/services/ga4InsightsService.js`：新增 `getAvailableKeyEvents(propertyId)` 呼叫新端點

### 步驟 4：測試 ✅ 已完成

- 後端：新增 11 個測試

  - `pytest -k ga4` 183 個測試全過（172 → 183，向下相容無影響）
- 前端：`vite build` 編譯驗證（步驟 3 已完成）；下拉顯示/重設邏輯屬單純狀態切換，UI 待人工在瀏覽器操作確認

### 步驟 5：GA4 API 相容性人工驗證（不可省略）

- 確認 `dimensions=["eventName"], metrics=["keyEvents"]`（近 7 天、不分 hour）這支新查詢對真實 GA4 property 能正常回應
- 確認 `keyEvents:{event_name}` 動態指標搭配告警規則既有的 `_fetch_metric_total`（含 `by_hour=True` 的 hourly 規則情境）對這個屬性實際存在的事件名稱都能正確查到觀測值與基線
